# agentic-principle

> 先判断该不该用 Agent，再定怎么拆、怎么编排、怎么验收——Agentic 方案的设计与评审原则。

[English](./README.md) · **中文**

一个 agent skill，把业务意图转成一份经过确认的 Agentic 方案：场景选型、Agent 与工具边界、系统提示词、上下文与并发预算、以及每一步之间的信息传递链路。它也能反过来用——作为评审视角，去审已经上线的系统。

## 为什么需要它

大多数 Agentic 项目出问题，都发生在写提示词之前。

- **没人问过这事到底要不要用 LLM。** 一个 40 行确定性脚本能解决的事，被重做成三个 Agent 协作——更慢、更贵、还更不可靠。
- **Scope 从来没被界定清楚。** Agent 上线之后才发现：它要做的那个业务判断所依据的规则，它根本读不到。于是它开始自由发挥，而且发挥得很有说服力。
- **子 Agent 派发没有上限。** 第一次真实负载就打爆 LLM 并发额度，事故看起来像 bug，其实是一个从没有人做过的容量决策。
- **系统提示词是化石。** 写过一次，业务逻辑早就变了，没人说得清它上一次被确认还有效是什么时候。
- **没有一份能指着看的设计。** 没人能说出方案是在哪一刻被敲定的，于是每次分歧都要把整件事重新吵一遍。

这些都不是提示词工程问题，是架构和范围界定问题——而且全都可以在动手前定下来。这个 skill 做的就是逼你把它们定下来。

## 它给你什么

**一套不能跳过的场景分类。** 五个场景，自上而下判定，第一个命中即答案。外加一张相邻场景边界表——因为"这是个工作流"和"这需要子代理"在你问对问题之前长得一模一样。

**一条复杂度阶梯。** 分类表给出场景的上限，阶梯要求你在上限内取最低可行档。每往上一级，都要多付延迟、成本和不确定性。

**每个系统提示词的六要素契约。** 角色 → 核心职责 → 处理流程 → 质量标准 → 输出格式 → 边界情况，一个都不能少。输出格式是最常被整项漏掉的那个，也正是它会让下游解析崩掉。

**一次强制的信息完备性扫描。** 在把设计拿给任何人看之前，逐个 Agent 节点核对：它要做的每一项业务判断，所依据的规则它真的读得到吗？缺口列成清单交给用户。**虚构业务规则来填补缺口是硬性禁止**，不是建议。

**默认不许用启发式规则替代语义判断。** "能程序化的尽量程序化"是对的，但它指的是**规则确定**的过程：格式转换、字段映射、权限判定、硬上限。**靠关键词、正则、阈值去猜语义意图的不算程序化**——那是把语义判断伪装成程序：样例上看着能跑，遇到没见过的表述就无声地判错，下游拿不到任何"我不确定"的信号。所以默认不引入；确需引入的要先给**覆盖率论证（至少覆盖 75% 的真实场景）+ 反例集 + 未覆盖部分的兜底**，三样都要用户确认。算不出覆盖率、举不出反例，说明这就该交给 Agent 判断。判断方法很简单：这条规则遇到没见过的输入会怎样？"安静地给个错答案"就是启发式，"明确报错或走兜底"才是确定性规则。顺带一提，**启发式用来缩小搜索范围可以，用来下判定不行**——这条同样约束 skill 自带的那个扫描脚本。

**一次强制的注意力负载检查。** 与完备性扫描配对的另一半：逐个 Agent 核对红线——提示词多长、首轮塞了多少可选资料、一个 Agent 被塞进几个场景、关键中间结论是不是只活在对话历史里。触线就必须处置：下沉、拆分、加路由、加检查点。减负只能靠换层级或拆职责，**不许删掉 Agent 做判断必需的规则**。

**每个动作都要标清"它能不能自己拍板"。** 授权表只说给了哪些工具，不说这个动作该由谁决定——而事故的典型形态恰恰是"调对了工具但不该由它自己决定"。所以每个工具/动作四选一标一档自主级别：只给建议 / 执行前需确认 / 可回滚范围内自动 / 不可逆的自动执行。最后一档**必须命名审批闸门**——谁审、在哪一步审、审不过怎么办，而且闸门必须是**确定性代码**：写在系统提示词里的"执行前请先确认"不算闸门，模型不遵守时没有东西拦得住。

**外部内容一律当数据，不当指令。** Agent 读到的每一份外部内容——网页、工具返回、用户上传的文件、**子 Agent 的产出**——都是潜在的注入载体，而子 Agent 的产出会被父 Agent 当事实采纳，污染沿链路向上传播。所以不可信内容以数据形式传入、绝不拼进系统指令位置；"注入内容永不改变目标与授权"这条提示词侧写死、工具层做兜底，两处缺一不可；输出侧检查逐条具名并配机器可读判定码；检查自身出错时 **fail-closed**——最容易写反的一条，很多实现的 `catch` 分支直接就把未检查的内容放行了。

**不让工具返回吃掉上下文。** 注意力检查管的是你塞给 Agent 多少，这一条管工具塞回来多少。一次超长的返回能吞掉整轮上下文预算，而它的大小由外部数据决定——设计时没问题，测试时没问题，上线撞上一个大仓库、一张宽表、一条长日志就爆。所以每个返回直接进上下文的工具与 MCP 都要按**最坏情况**估一遍体量，超过 10k token 的必须给出处置：**在 agent loop 里统一落盘**（循环发现超阈值就写文件，回给模型的是路径 + 摘要 + 检索方式——一处实现，覆盖你现有和将来的所有工具，包括改不动的第三方 MCP），或者**由工具自己兜住**（服务端过滤、分页、默认摘要）。选了后者就欠一条极端返回用例：构造最坏输入、实测 token 数、落成回归。实测仍超 10k，skill 会停下来问你要不要改走落盘——"一般不会那么大"不算处置。落盘也不等于把信息丢掉：返回里必须留下总量、结构和检索路径，而且落盘的内容读回来仍是不可信输入，不因为存成了本地文件就变可信。

**Agent 必须停得下来。** 自建 agent loop 时，终止条件只有三种合法写法：**可外部验证的完成**、撞上限、带证据放弃。模型说"我做完了"不是完成证据——文件真的变成了期望的样子、测试转绿、接口回查到状态，才是。四类上限（步数 / 时间 / 成本 / 连续失败）一个都不能少，而且撞上限**不许静默返回**：调用方必须能从返回值里程序化地分辨"这是想清楚了"还是"这是被砍断了"，还要拿到进度、原因和续跑入口。

**出错之后的路径要先设计好。** 先给错误分四类（可重试 / 可纠正 / 可降级 / 终止）再谈重试——把"参数写错了"和"网络抖了一下"当同一回事处理，是重试三次然后一样失败的根源。重试要有界、要带抖动，**有副作用的动作没有幂等键就不许自动重试**（否则重试就是重复扣款的生成器）。还有一类 Agent 特有的失败：不报错但也不前进——同样的工具、同样的参数反复调用。这个必须在 loop 侧用代码检测，在系统提示词里写"请不要重复调用"没有用，模型卡住的时候恰恰最不遵守纪律。

**记住什么、谁读得到，是两件要分开定的事。** 把整段对话历史当长期记忆存下来，是这一维几乎所有事故的起点。轨迹、运行时状态、用户记忆、业务状态、共享知识五者要分开，各有各的生命周期与信任级别。检索的**过滤必须发生在内容进入模型上下文之前**，而且过滤条件要从会话认证身份取——让模型自己传 `tenant_id` 等于没有隔离，注入一句话就能改掉它。不可信内容可以作为素材被记录，但不能直接变成 Agent 遵循的规则，否则一次性的注入会被固化成永久生效的注入。

**成本要按一次任务算，不是按一次调用算。** 只统计 output token 会严重低估——上下文随轮次累积，第 20 轮的单轮 input 可能是第 1 轮的十几倍，再算上重试、失败调用和子 Agent 展开。延迟看 p95/p99，均值会被大量快请求拉低而掩盖长尾。还有一条几乎零成本却常年被忽略的：**prompt cache 按前缀匹配生效**，所以静态的系统提示词与工具目录放前面、每轮变的东西一律追加到尾部；在提示词开头注入一个当前时间戳，就能让缓存 100% 失效、成本翻数倍——而那个时间戳往往根本没被用到。

**长产物不许一口气吐出来。** 交付物一长，就改成「程序预建模板 → Agent 分区多次编辑 → 程序校验」：不撞单次输出上限，每轮注意力只落在当前分区，出错只重填一个区而不是全文，模板本身框定了内容、漏了程序会点名补。多 Agent、多步骤的工作流默认先按这个思想编排——先定模板与分区表，再排谁填哪一区。

**每一步都要能单独验证。** 端到端跑通不算测过——它只告诉你"坏了"，不告诉你"哪一步坏了"，而 Agentic 的错误会沿链路传播、被下游的自由发挥掩盖。所以工作流和父子架构的**每个步骤**都要有独立用例；能程序断言的一律程序断言；非结构化产出交给专门的评测 Agent，输出结构化判定 + 证据，rubric 每条必须有判分锚点，**judge 上岗前先用人工标注样本校准**；上了规模就建评测集，由程序批量跑出通过率，修过的缺陷沉淀成回归样本。

**双轨核对。** 结构化提问每批不超过 4 项，然后出带流程图的设计文档终审。用户没签字之前，设计就不算"已确认"，而且 skill 会记下确认的时间和范围。

**给既有平台加能力的轻量入口。** 真实项目里最高频的场景不是从零建 Agent，而是在一个已经跑着的平台上加一个 skill、一个工具、一个配套服务。走完整新建流程太重，会被绕过；绕过之后新增能力的授权、注意力、测试就都没人管了。所以有第三条入口：**声明继承 + 只写增量 + 平台缺口清单**——继承项只写"继承自哪里"不复述（复述会漂移，漂移的复述比空白更危险），只 spec 本次新增的部分，然后逐条对照平台已知缺口本次有没有踩中：能补的补，补不了的显式登记为风险，**不允许"平台一直这样，那就这样吧"**。

**评审模式。** 指向一个已有实现，它会**先**独立推导出自己的设计，再做差异比对——这样才能抓住那些"直接读代码就会被锚定住"的场景选型错误。然后：

- **先声明审计模式**（只有文档 / 有代码 / 有运行证据）。设计稿不因为"没有代码"被扣分，但也不会拿到"可以上线"的结论。
- **逐维给证据状态**（pass / partial / fail / unknown / N/A）。拿不到证据是 `unknown`，必需的控制确实不存在才是 `fail`——把这两个混用，一头制造假问题，一头放过真问题。
- **注意力、成本、多 Agent 必要性走两段式**：带证据呈现问题 → 你确认这确实是问题 → 才给改进建议。这类现象常有你已知的业务理由，未经确认就给建议只会变成噪声。
- **安全、返回体量、终止条件、幂等、租户隔离不走两段式**：这些是客观缺陷不是权衡，带证据直接给建议（证据要实测——租户隔离尤其不接受代码走查代替实测）。修不修由你定。
- **收尾必跑矛盾检查**：提示词承诺 vs 工具实际权限、声称完成 vs 环境状态、重试 vs 幂等、图上的"独立评审" vs 实际信息流、评测结论 vs 样本量。这类问题在逐维检查里天然看不见——两处各自都合理，合起来才对不上。
- **一个 P0 不会被其他维度的优点抵消**，也不写成"总体良好但……"。阻断项永远置顶。

全程不擅自改动你的实现。

**排障模式。** 上线之后 Agent 行为不对劲——跑偏、该调的工具不调、结论凭空出现、停不下来、偶发失败——第四条入口专门处理这件事，而且它只做一件事：**先读对话记录，再猜**。

- **对话记录是唯一的一手证据。** 代码、提示词模板、配置、应用日志都只说明"本应如此"，transcript 说明"当时如此"——而这两者对不上本身就是最高频的一类根因。拿不到记录时，第一动作是把记录补上并复现，不是继续猜；同时这件事本身按 P0 登记，因为**没有可读的对话记录，等于这个系统的每一次异常都只能靠猜**。
- **先降噪成骨架时间线再读。** 一次真实运行动辄几十万 token，硬读就是把自己的上下文打满、然后被迫抽样，而抽样恰恰会漏掉根因。所以筛掉 thinking 全文、工具入参与返回全文，**只留角色、轮次、工具名、成败、体量、`stop_reason` 和入参指纹**——一屏扫完。入参指纹是这里最值钱的派生字段：它让"同一个工具用同一组参数反复被调"一眼可见，而光看工具名是看不出来的。
- **从头正序找第一偏离点，不从报错处倒着看。** Agent 的错误会沿轮次搬运放大：第 5 轮读错一个字段，第 30 轮才表现成一个很自信的错误结论；报错那一轮通常只是最后一块骨牌，那里的代码往往根本没毛病。
- **偏离分三类**：**输入偏离**（这一轮它实际看到的东西就是错的——换谁都会判错）、**决策偏离**（信息给到了，判断没做对）、**执行偏离**（想对了，动作没生效或结果没回来）。判输入偏离**必须看那一轮实际发出的 request**，不是模板、不是配置文件：变量没渲染、上下文被裁剪切掉、工具压根没进 `tools` 清单——这些在模板里全都看不见。**多数被归因为"模型不听话"的案例，实际是输入偏离。**
- **然后分四层归因**：harness（你自己的提示词拼装、上下文裁剪、工具注册、loop 控制——命中率最高的一层）、供应商（模型版本、限流、截断、格式变更）、外部程序（MCP server、业务 API、DB、沙箱）、最后才是设计本身。顺序有讲究：一上来就读提示词找毛病几乎总能"找到点什么"，然后你改了提示词、异常碰巧不复现，根因被埋进去，下次换个输入原样复发。
- 所以有一条硬禁止：**没读过对话记录不许改提示词止血**。同理，"改了提示词就不复现了"不算定位。
- **收口四件事**：归因写明层与证据、映射回 D1–D12 给处置、补一条回归用例、如实说明哪些结论仍是 `unknown`。根因要是落在"这一维压根没做"，那它就不是偶发故障而是架构缺陷——升级为评审或重新设计，不要就地打补丁。

## 场景分类

| 判定问题（自上而下，第一个命中即答案） | 场景 | 例子 |
|---|---|---|
| 流程完全确定，且每一步都不需要语义判断？ | **完全程序过程** | 批量重命名文件；按固定规则生成月度报表 |
| 只需产出文本／建议，不需调用工具改变或获取外部状态？ | **单 Agent Chat** | 内部规章问答；文案润色 |
| 步骤次序、分支在设计期即可穷举，由程序编排？ | **Agentic 工作流** | 合同审阅流水线：解析 → 并行审阅 → 汇总报告 |
| 任务拆解方式只有运行时才知道，或需要并行／上下文隔离？ | **父子 Agentic** | 陌生代码库全量安全审计 |
| 以上都不是——以 Agent 为中心，用户直接对话，Agent 自主调用工具 | **单 Agentic** | 结对编程助手 |

命中"完全程序过程"时，skill 会让你停止使用它。这是设计意图，不是缺陷。

判错基本都发生在相邻场景之间，所以另有一张表专门切这四条边界——比如**工作流 vs 父子 Agentic**，分界线只有一个问题：子任务清单是设计期已知，还是要等 Agent 去探查了才知道？

工作流场景下还有第二层选择，编排模式取自 [Anthropic 官方 Building Effective Agents](https://www.anthropic.com/research/building-effective-agents)：Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer。

## 工作流

| 步骤 | 做什么 |
|---|---|
| 0 | 理解意图与边界——愿景、用户、成功标准、明确的不做什么 |
| 1 | 场景分类，然后在该场景上限内取复杂度阶梯的最低可行档 |
| 2 | 会话内形成设计草案，此时不落盘 |
| 2.5 | **逐维检查**——按下面这张维度矩阵逐维执行，不适用的标 `N/A` 并写明理由 |
| 3 | 双轨核对：分批提问，再出设计文档终审 |
| 4 | 实现，或与既有系统做差异比对。每个 Agent 实跑测试、每个步骤有独立用例跑通，才算完成 |

四条入口：**新建**走完整流程；**增量**（只在既有平台上加 skill / 工具 / 服务）走继承声明 + 缺口清单的精简路径；**评审**先独立设计再比对；**排障**（已上线 Agent 出了具体异常）不走这套步骤，直接读对话记录定位根因。

## 维度矩阵

设计侧的逐维检查与评审侧的逐维评估共用这一张表——单一真相源，不是两套标准。每维先判适用条件，适用的逐个对象核对红线。

| # | 维度 | 适用条件（否则 N/A） | 红线举例 |
|---|---|---|---|
| D1 | 信息完备性 | 全部 | 存在无规则依据的业务判断；用启发式规则顶替本该由用户提供的规则 |
| D2 | 输入侧注意力 | 全部 | 系统提示词 > 10000 字符；职责跨 3 个以上不相干领域；变动内容置于提示词前部打断 prompt cache |
| D3 | 产物侧构造 | 有较长交付物 | 预估产出超过模型单次输出上限的一半 |
| D4 | 工具返回体量 | 有直接进上下文的工具/MCP | 最坏情况单轮累计 > 10k token 且无兜底 |
| D5 | 授权与安全边界 | 全部 | 高影响动作无具名闸门；闸门写在提示词里而非程序侧；安全检查 fail-open |
| D6 | Loop 与终止 | 自建 agent loop | 终止只依赖模型自述"我完成了"；四类上限缺任一 |
| D7 | 可靠性与恢复 | 有副作用动作或外部依赖 | 有副作用的重试不幂等；重复的相同工具调用未被识别为无进展 |
| D8 | 记忆与隐私 | 有持久记忆、RAG 或跨会话状态 | 检索未在入上下文前按身份/租户过滤；不可信内容可直接写入持久记忆 |
| D9 | 成本与性能 | 上规模或有预算/延迟约束 | 无任务级成本或时间上限；只看均值不看 p95/p99 |
| D10 | 多 Agent 链路 | ≥ 2 个 Agent | 未与单 Agent 基线对比；handoff 丢失验收标准；评审者拿不到原始证据 |
| D11 | 测试与评测 | 全部 | 多节点场景只有端到端测试；评测 Agent 未用人工标注样本校准 |
| D12 | 可观测与回放 | 全部 | 要改代码才能观察；关闭调试模式后连骨架都不留；只留末端产物、中间环节无切片；无法只回放某一个环节 |

新增一个维度只是往表里加一行——这是这一版重构的主要目的：以前它们是 `2.5 / 2.6a / 2.6b / 2.6c / 2.7` 这样一串越排越畸形的编号。

## 安装

```bash
git clone git@github.com:weidwonder/agentic-principle.git
cp -r agentic-principle/agentic-principle ~/.claude/skills/
```

或者把 clone 留在你惯用的开发目录，软链子目录过去，这样 `git pull` 就能直接更新已安装的 skill：

```bash
ln -s "$PWD/agentic-principle/agentic-principle" ~/.claude/skills/agentic-principle
```

skill 目录自包含——无需登录、无第三方依赖。`scripts/scan_agent.py` 是评审时的**可选**加速器，只用 Python 标准库，不用它也不影响 skill 的任何流程。

## 怎么用

用大白话说你要什么：

- "帮我设计合同审阅功能的 Agent 架构"
- "这个场景该做成工作流，还是让 Agent 派子代理？"
- "给现有的运维 Agent 加一个能改线上配置的工具"
- "评审一下我们上季度上线的那套 Agent 系统"
- "这个 Agent 最近老是不调工具、直接瞎猜，帮我看看是怎么回事"

它会先给出场景分类结论和判定理由，然后开始提问。如果你的想法过度设计了，它会顶回来；如果答案是"这事写个脚本就行"，它也会直说。

## 非目标

它不写你的业务代码，也不负责生成插件形态的 agent 配置文件——那是 `agent-creator` / `agent-development` 的职责。它也不审查 Skill 本身写得好不好（触发词准不准、结构合不合规、有没有孤立文档）——那是 `skill-principle` 的职责。两者互补：一个 Skill 若实质是一套 Agent 编排，这个 skill 审它的架构，`skill-principle` 审它的写法。它负责设计架构，实现交给别人。

它也不会让你悄悄跳过核对。你可以明确要求跳过，它会照做——但会把它据以推进的每一条假设都写下来，并告诉你都是哪些。

# agentic-principle

> 先判断该不该用 Agent，再定怎么拆、怎么编排、怎么验收——Agentic 方案的设计与评审原则。

[English](./README.md) · **中文**

一个 agent skill，把业务意图转成一份经过确认的 Agentic 方案：场景选型、Agent 与工具边界、系统提示词、上下文与并发预算、以及每一步之间的信息传递链路。它也能反过来用——作为评审视角，去审已经上线的系统。

## 为什么需要它

大多数 Agentic 项目出问题，都发生在写提示词之前。

- **没人问过这事到底要不要用 LLM。** 一个 40 行确定性脚本能解决的事，被重做成三个 Agent 协作——更慢、更贵、还更不可靠。
- **Scope 从来没被界定清楚。** Agent 上线之后才发现：它要做的那个业务判断所依据的规则，它根本读不到。于是它开始自由发挥，而且发挥得很有说服力。
- **子 Agent 派发没有上限。** 第一次真实负载就打爆 LLM 并发额度，事故看起来像 bug，其实是一个从没有人做过的容量决策。
- **系统提示词是化石。** 写过一次，业务逻辑早就变了，没人说得清它上一次被确认还有效是什么时候。
- **没有一份能指着看的设计。** 没人能说出方案是在哪一刻被敲定的，于是每次分歧都要把整件事重新吵一遍。

这些都不是提示词工程问题，是架构和范围界定问题——而且全都可以在动手前定下来。这个 skill 做的就是逼你把它们定下来。

## 它给你什么

**一套不能跳过的场景分类。** 五个场景，自上而下判定，第一个命中即答案。外加一张相邻场景边界表——因为"这是个工作流"和"这需要子代理"在你问对问题之前长得一模一样。

**一条复杂度阶梯。** 分类表给出场景的上限，阶梯要求你在上限内取最低可行档。每往上一级，都要多付延迟、成本和不确定性。

**每个系统提示词的六要素契约。** 角色 → 核心职责 → 处理流程 → 质量标准 → 输出格式 → 边界情况，一个都不能少。输出格式是最常被整项漏掉的那个，也正是它会让下游解析崩掉。

**一次强制的信息完备性扫描。** 在把设计拿给任何人看之前，逐个 Agent 节点核对：它要做的每一项业务判断，所依据的规则它真的读得到吗？缺口列成清单交给用户。**虚构业务规则来填补缺口是硬性禁止**，不是建议。

**一次强制的注意力负载检查。** 与完备性扫描配对的另一半：逐个 Agent 核对红线——提示词多长、首轮塞了多少可选资料、一个 Agent 被塞进几个场景、关键中间结论是不是只活在对话历史里。触线就必须处置：下沉、拆分、加路由、加检查点。减负只能靠换层级或拆职责，**不许删掉 Agent 做判断必需的规则**。

**长产物不许一口气吐出来。** 交付物一长，就改成「程序预建模板 → Agent 分区多次编辑 → 程序校验」：不撞单次输出上限，每轮注意力只落在当前分区，出错只重填一个区而不是全文，模板本身框定了内容、漏了程序会点名补。多 Agent、多步骤的工作流默认先按这个思想编排——先定模板与分区表，再排谁填哪一区。

**每一步都要能单独验证。** 端到端跑通不算测过——它只告诉你"坏了"，不告诉你"哪一步坏了"，而 Agentic 的错误会沿链路传播、被下游的自由发挥掩盖。所以工作流和父子架构的**每个步骤**都要有独立用例；能程序断言的一律程序断言；非结构化产出交给专门的评测 Agent，输出结构化判定 + 证据，rubric 每条必须有判分锚点，**judge 上岗前先用人工标注样本校准**；上了规模就建评测集，由程序批量跑出通过率，修过的缺陷沉淀成回归样本。

**双轨核对。** 结构化提问每批不超过 4 项，然后出带流程图的设计文档终审。用户没签字之前，设计就不算"已确认"，而且 skill 会记下确认的时间和范围。

**评审模式。** 指向一个已有实现，它会**先**独立推导出自己的设计，再做差异比对——这样才能抓住那些"直接读代码就会被锚定住"的场景选型错误。比对里含注意力负载评估：问题项带证据呈现，**先跟你确认这确实是问题**，确认成立才给改进建议，绝不擅自改动你的实现。

## 场景分类

| 判定问题（自上而下，第一个命中即答案） | 场景 | 例子 |
|---|---|---|
| 流程完全确定，且每一步都不需要语义判断？ | **完全程序过程** | 批量重命名文件；按固定规则生成月度报表 |
| 只需产出文本／建议，不需调用工具改变或获取外部状态？ | **单 Agent Chat** | 内部规章问答；文案润色 |
| 步骤次序、分支在设计期即可穷举，由程序编排？ | **Agentic 工作流** | 合同审阅流水线：解析 → 并行审阅 → 汇总报告 |
| 任务拆解方式只有运行时才知道，或需要并行／上下文隔离？ | **父子 Agentic** | 陌生代码库全量安全审计 |
| 以上都不是——以 Agent 为中心，用户直接对话，Agent 自主调用工具 | **单 Agentic** | 结对编程助手 |

命中"完全程序过程"时，skill 会让你停止使用它。这是设计意图，不是缺陷。

判错基本都发生在相邻场景之间，所以另有一张表专门切这四条边界——比如**工作流 vs 父子 Agentic**，分界线只有一个问题：子任务清单是设计期已知，还是要等 Agent 去探查了才知道？

工作流场景下还有第二层选择，编排模式取自 [Anthropic 官方 Building Effective Agents](https://www.anthropic.com/research/building-effective-agents)：Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer。

## 工作流

| 步骤 | 做什么 |
|---|---|
| 0 | 理解意图与边界——愿景、用户、成功标准、明确的不做什么 |
| 1 | 场景分类，然后在该场景上限内取复杂度阶梯的最低可行档 |
| 2 | 会话内形成设计草案，此时不落盘 |
| 2.5 | **信息完备性检查**——逐个 Agent，不允许抽样，产出缺口清单 |
| 2.6a | **输入侧注意力负载检查**——逐个 Agent 核对红线，触线项给出下沉 / 拆分 / 加路由 / 加检查点 |
| 2.6b | **产物侧构造检查**——命中长产物判据的，当场定出模板分区表与程序侧校验规则 |
| 3 | 双轨核对：分批提问，再出设计文档终审 |
| 4 | 实现，或与既有系统做差异比对。每个 Agent 实跑测试、每个步骤有独立用例跑通，才算完成 |

## 目录里有什么

skill 本体是 `agentic-principle/` 子目录，它才是分发单位；仓库根目录的两份 README 不属于 skill。

```
agentic-principle/
├── SKILL.md
└── references/
    ├── agent-construction.md
    ├── system-prompt-blocks.md
    ├── design-doc-template.md
    ├── long-artifact.md
    ├── testing.md
    └── review-mode.md
```

| 文件 | 内容 |
|---|---|
| `SKILL.md` | 入口。场景分类、工作流、基础原则、各场景确认清单、绝对禁止条目 |
| `references/agent-construction.md` | 六要素提示词模板、写作细则、最小能力集、实跑测试步骤 |
| `references/system-prompt-blocks.md` | 12 个可复用系统提示词块 + 适用条件矩阵，其中一个必选 |
| `references/design-doc-template.md` | 权威提问批次、设计文档骨架、流程图写法 |
| `references/long-artifact.md` | 长产物的三步做法、分区划法、完整示例 |
| `references/testing.md` | 三层测试执行要点、步骤级用例、评测 Agent 与 rubric、批量评测与门禁 |
| `references/review-mode.md` | 评审模式的四项评估、证据要求、边界 |

全文的工具名都写成**能力类别**（文件读取、内容检索、路径匹配、写入、命令执行、网络访问、子代理派发），不绑定任何一个 harness 的具体工具名。使用时按你的实际环境映射。

## 安装

```bash
git clone git@github.com:weidwonder/agentic_principle.git
cp -r agentic_principle/agentic-principle ~/.claude/skills/
```

或者把 clone 留在你惯用的开发目录，软链子目录过去，这样 `git pull` 就能直接更新已安装的 skill：

```bash
ln -s "$PWD/agentic_principle/agentic-principle" ~/.claude/skills/agentic-principle
```

skill 目录自包含——无 CLI、无依赖、无需登录。

## 怎么用

用大白话说你要什么：

- "帮我设计合同审阅功能的 Agent 架构"
- "这个场景该做成工作流，还是让 Agent 派子代理？"
- "评审一下我们上季度上线的那套 Agent 系统"

它会先给出场景分类结论和判定理由，然后开始提问。如果你的想法过度设计了，它会顶回来；如果答案是"这事写个脚本就行"，它也会直说。

## 非目标

它不写你的业务代码，也不负责生成插件形态的 agent 配置文件——那是 `agent-creator` / `agent-development` 的职责。它负责设计架构，实现交给别人。

它也不会让你悄悄跳过核对。你可以明确要求跳过，它会照做——但会把它据以推进的每一条假设都写下来，并告诉你都是哪些。

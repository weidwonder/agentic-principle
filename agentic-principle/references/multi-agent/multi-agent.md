## 一、先问：为什么要多个

多 Agent 会成倍放大成本、延迟与故障面。它必须带来至少一项**实质收益**：

| 收益 | 判据 | 不成立的样子 |
|---|---|---|
| **新信息** | 子 Agent 通过执行、渲染、检索、测量拿到了父 Agent 没有的东西 | 子 Agent 读的是同一份上下文，只是换个说法复述 |
| **真并行** | 相互独立的任务同时跑，显著缩短墙钟时间 | 任务其实有依赖，只能串行等 |
| **上下文隔离** | 把嘈杂的探查过程挡在主线程之外 | 隔离出去的东西最后又全量倒回主上下文 |
| **专用能力** | 需要不同的工具集、模型或模态 | 所有 Agent 工具集与模型完全相同 |
| **独立控制** | 审批、授权、职责分离的需要 | 评审者与被评审者由同一段逻辑驱动 |

**几个 Agent 看着同一份证据各说一遍，不构成独立验证。** 它们的错误是相关的——上游一个幻觉，会被下游一致地复述，反而显得更可信。

**必须与单 Agent 基线对比。** 设计文档里要写清：同样的任务，一个设计良好的单 Agent 能做到什么程度、成本与延迟各是多少、多 Agent 方案多花的部分换来了什么。写不出这个对比，就是没论证。

## 二、两个正交决策

这两件事要**分开决定**，不要互相推导：

1. **上下文共享方式**：全共享（都看得到同一条轨迹）／完全隔离（各有各的上下文，靠 handoff 传递）／混合（共享摘要 + 各自私有细节）。
2. **拓扑**：对等循环／Manager-Worker 编排／去中心化交接／固定工作流。

共享的群聊也可以是中心化控制的，隔离的 Agent 也可以被集中调度。把两者绑在一起想，会漏掉很多合理组合。

上下文共享方式直接决定 §三 的 handoff 契约有多重要：**越隔离，契约越要写全**。

## 三、handoff 契约

上下文隔离时，交接内容就是下游 Agent 能看到的**全部**。缺一项，下游就得靠猜。

必含字段：

| 字段 | 缺了会怎样 |
|---|---|
| **任务与它为什么重要** | 下游做了个技术上正确、方向上跑偏的东西 |
| **验收标准与停止条件** | 做过头或做不够，且无法自检 |
| **已确认的事实与约束** | 重新探查一遍（浪费），或违反上游已定的约束 |
| **未决问题** | 下游擅自替用户做了决定 |
| **可用工具、权限** | 无权限时反复重试，或越权操作 |
| **预算**（步数 / 时间 / token） | 子 Agent 的开销不受控，见 §五 |
| **产物引用与期望输出结构** | 上游拿到无法解析的东西 |
| **所给证据的来源与新鲜度** | 拿着过期数据当现状用 |

**不要把上游的完整轨迹整段转发。** 试错历史多数是噪声，而决定性的约束与证据才是信号。整段转发既浪费上下文，又会让下游被上游的思路锚定——这恰恰抵消了上下文隔离本该带来的好处。

## 四、角色与接口质量

每个 Agent 都要满足：

- 职责与其他角色**不实质重叠**；
- 只拿完成该职责所需的**最小数据与工具**；
- 有结构化的输入输出契约；
- 最终集成与环境验证**有明确的负责方**；
- 失败、超时、取消、升级的行为已定义。

**判据**：替换其中一个 Agent，是否需要改写其他所有角色？需要，说明接口耦合过紧。

## 五、并发与任务拆分

在不损失质量的前提下，把相互独立的任务拆小、提高并发，以降低总耗时。四条约束：

- **相互独立**：拆出的任务之间不共享可变状态、不依赖彼此产出。有依赖的用流水线串联，不要硬并发。
- **不超过并发上限**：并发数受限于已确认的 LLM 并发额度。这是**硬约束**，设计文档里写死具体数值。
- **不因拆分损失质量**：需要全局视野的判断（跨文件综合、去重、排序、一致性校验）不要拆散；拆分后必须有汇总节点。
- **写明量化值**：拆分粒度与并发数是设计文档中写死的量化项，不是运行时随意决定。

**预算要沿调用树累计**，不是每层各设各的：父 Agent 的总预算必须覆盖所有子 Agent 开销之和。三层嵌套、每层 5 个子 Agent，实际展开是 125 个——这是成本失控最常见的形态。派发前先算树的规模上界。

**并行的收益按最慢那条算**，不是平均。有一个子任务特别慢时，并行几乎不省时间，却付了全部的并发成本。

## 六、共享写入

多个 Agent 写同一批文件或记录时，必须有并发控制。可选方案：

| 方案 | 适用 | 注意 |
|---|---|---|
| **分区独占** | 能按文件/分区切干净 | 最简单也最可靠，优先选这个（配合 `../delivery/long-artifact.md` 的分区表） |
| **乐观版本检查** | 冲突较少 | 冲突时要有明确的重试或合并规则 |
| **隔离分支 / worktree** | 代码类改动 | 要定清楚谁负责合并 |
| **串行化写入节点** | 写操作不频繁 | 由一个节点统一落盘，其他只产出内容 |

**文件级锁挡不住跨文件的语义冲突**：两个 Agent 各改各的文件，各自都对，合起来不自洽（一个改了接口签名，另一个还在按旧签名调用）。这类冲突要靠依赖感知的调度顺序 + 一个全局一致性校验节点来兜，不是靠锁。

## 七、Manager-Worker

Manager 型节点逐项检查：

- 拆解是否落在**真实的独立边界**上（而不是为了并行硬切）；
- 是否给每个 worker 明确的契约与**成比例的预算**；
- 是否能跟踪 worker 状态而**不必把它们的原始上下文全部吸回来**；
- 成功或失败后能否**取消兄弟任务**；
- 超时、部分结果、重复完成事件怎么处理；
- **是否拿 worker 的摘要与原始产物核对过**；
- Manager 自己是不是一个没人审查的语义单点。

最后一条最容易被忽略：所有信息都经 Manager 汇总，它的一次误读会污染整个结论，而链路里没有任何环节能发现。缓解办法是让关键结论保留可追溯的原始证据引用，允许下游或用户回溯核对。

## 八、评审者独立性

生成-评审、提议-审批这类结构，评审方要有**独立的证据或视角**才有价值：

- 优先给它**独立证据**：测试输出、编译结果、渲染截图、数据库状态、原始文档——而不是上游的结论。
- 只拿到"上游说这样做是对的"就去评审，等于让它投一张附议票。
- 条件允许时用**不同模型族**做评审方，减少同源盲区。
- 评审方要有**否决权**，但不应该有"自己改完自己批准"的权限。

**一致不等于正确。** 上游的错误会随着下游的一致复述而显得更可信——这是多 Agent 系统里最隐蔽的失效模式。

## 九、消息与生命周期

Agent 之间靠消息通信时，消息要带：发送方、接收方或主题、消息类型、任务 ID、序号或时间戳、结构化载荷。另查：

- 鉴权与授权（不是同一个产品派生出来的就默认可信）；
- 去重与幂等（做法见 `../runtime/reliability.md` §五）；
- 顺序与陈旧消息处理；
- 投递失败与重试；
- 发现/列举、发消息、取消/终止、等待、取结果这几种操作的语义是否完整；
- 收尾清理：进程、浏览器、锁、临时文件。

**对等交接必须有跳数上限或环检测**，群体讨论必须有进展判据与终止条件——否则会 livelock：所有 Agent 都很忙，任务却不前进。这与 `../runtime/reliability.md` §三 的无进展检测是同一件事在多 Agent 层面的体现。

## 十、子 Agent 产出的信任

**子 Agent 的产出是不可信输入**，信任级别继承其输入中最低的那一路。

父 Agent 采纳前要做筛查：子 Agent 读了哪些不可信来源、产出里有没有夹带指令性文字、结论有没有原始证据支撑。不因为"是我派出去的"就当可信——污染会沿链路向上传播，且传播过程中来源标注最容易丢失。

信任分级表与处理要求见 `../safety/safety.md` §一。**这是父子架构最容易漏的一处**。

同时：每个子 Agent 的工具与数据都按最小权限给，不要因为父 Agent 有权限就把权限整体下发。

## 十一、常见失败模式

- 角色重叠、归属不清，同一件事两个 Agent 都以为对方在做；
- handoff 丢失约束或验收标准，下游做出方向正确但不合格的东西；
- Manager 只看摘要做决策，从不回看原始产物；
- 共享文件丢更新，或跨文件语义冲突；
- 一个幻觉被下游一致复述而获得可信度；
- 评审者与提议者共享同样的假设与证据；
- 无上限的派生、辩论、交接循环；
- 每个 worker 本地都完成了，但没有任何环节验证整合后的结果；
- 名义上并行、实际有依赖的任务被硬并发。

## 十二、用例

D10 触线的实现，交付前至少跑通这五条：

1. **单 Agent 基线对比**：同一批任务用单 Agent 方案跑一遍，记录成功率、成本、延迟，与多 Agent 方案对比。**这是论证的证据，不是可选项。**
2. **handoff 完整性**：抽查若干条交接记录，核对 §三 的字段是否齐全；故意去掉一个字段，确认下游能识别并报缺而不是自由发挥。
3. **并发冲突**：让两个 Agent 同时写同一个目标，确认并发控制生效、没有丢更新。
4. **取消传播**：中途取消父任务，确认子 Agent 确实停止、资源被清理、已产生的副作用被明确列出。
5. **注入沿链路传播**：在子 Agent 会读到的内容里埋一句指令性文字，确认它不会经由子 Agent 的产出改变父 Agent 的目标或授权。

第 5 条属于安全切片，长期保留为回归样本。

## 常见症状

| 症状 | 动作 |
|---|---|
| 多个 Agent 结论高度一致，但最终结果还是错的 | 一致不等于正确（§八）。它们多半看的是同一份证据——给评审方独立证据，或换一个模型族 |
| 下游 Agent 做出来的东西方向对但不合格 | handoff 丢了验收标准或关键约束（§三）。逐字段核对交接内容 |
| 并行跑完合起来不自洽（改了接口签名但调用方没跟着改） | 跨文件语义冲突，文件级锁挡不住（§六）。加依赖感知的调度顺序 + 全局一致性校验节点 |
| 子 Agent 越派越多，成本失控 | 预算没沿调用树累计（§五）。派发前先算树的规模上界，父预算必须覆盖子开销之和 |

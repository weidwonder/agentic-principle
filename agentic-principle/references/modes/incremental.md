# 在既有 Agent 上加能力

入口判定为「增量」时读：目标平台的场景选型、编排模式、agent loop 已定且本次不动，只新增 skill / 工具 / 配套服务。新建与评审场景不读此文件。

核心做法：**声明继承 + 只写增量 + 逐条对照平台缺口**。省的是重复论证，不是省该做的判断。

目录：

- §一 入口判定与退回信号
- §二 继承声明
- §三 只 spec 增量
- §四 平台缺口清单
- §五 各步骤怎么走
- §常见症状

## 一、入口判定与退回信号

三条同时满足才走增量入口：

1. 目标平台已有稳定运行的实现，其场景分类、编排模式、agent loop 与轮次上限本次**不改**。
2. 本次只新增 skill / 工具 / 配套服务，**不改既有 Agent 的职责边界**。
3. 新增能力不会突破已确认的并发上限与上下文上限。

任一条不满足 → 退回「新建」入口走完整流程。典型退回信号：

- 新增能力需要派子代理 → 改变了编排模式
- 新增能力要求提高并发或加长上下文 → 动了资源上限
- 新增能力让某个 Agent 的职责跨到第 3 个不相干领域 → 该拆 Agent，不是加工具

不确定时按新建走。判错方向的代价不对称：多论证一次只是费时间，少论证一次会把架构问题埋进平台。

## 二、继承声明

增量设计文档的第一节。写清从平台基线继承了什么、本次不重新论证。

**继承项清单（10 项）见 `../delivery/design-doc-template.md` §五 增量骨架的「2. 继承声明」一节**——那里是文档骨架的权威所在，此处不复制一份，避免两处漂移。本节只给填写纪律：

**只写"继承自哪里"，不复述内容。** 复述会与平台真实状态漂移，而漂移的复述比空白更危险——读者会信它。

某项找不到继承来源（平台既没文档、也指不出代码位置）时，它就不是"继承"而是"未知" → 登记进 §四 的缺口清单，不要含糊写"沿用现有做法"。

## 三、只 spec 增量

设计文档只写本次新增的部分：

- 新增工具 / skill 的职责、输入输出契约、隐式规则（按 `../tools/tool-design.md`）
- 它的**自主级别**；若为 `high-impact-automation`，写清审批闸门（谁审、在哪一步审、审不过怎么办）
- 它对并发预算与上下文预算的**占用增量**（增量，不是总量）
- 它按最坏情况估算的**最大返回体量**、是否触 10k 红线、靠平台落盘机制兜住还是本工具自兜底（见 `../tools/tool-output.md`）
- 它引入的**新不可信输入来源**，以及对应的处理位置
- 它需要的新测试用例与评测样本

其余一律指向平台基线文档，不复制。

## 四、平台缺口清单（Gap Watchlist）

增量场景最关键的一节。既有平台往往带着已知但没修的缺陷，做增量时**逐条对照本次新增能力是否踩中**：

| 平台缺口 | 本次是否踩中 | 处置 |
|---|---|---|
| 无统一审批闸门 | 是——新工具会写生产数据 | 在本能力内加确定性确认步骤 |
| 无 turn 上限 | 否——本次不改 loop | 登记为平台级风险，本次不处理 |
| 工具返回未做注入筛查 | 是——新工具会拉取外部网页 | 在本能力内对返回做筛查 |
| loop 侧无超长返回落盘机制 | 是——新工具会拉全量日志 | 在本工具内做分页 + 落盘，并建极端返回用例 |
| 无步骤级用例 | 是——新增能力含 3 个节点 | 新增节点补齐用例，存量不动 |

处置只有三种，**不存在第四种"平台一直这样，那就这样吧"**：

1. 能在能力层顺手补的 → 补（给新工具单独加一道确认、单独对返回做筛查、给新节点补用例）。
2. 补不了的（要动平台才能修）→ **显式登记为风险并标注影响**，交用户裁决，不静默继承。
3. 本次未踩中的 → 记"未踩中"，不处理，但保留在清单里供下次增量复用。

常见缺口起手式，逐条问一遍：无审批闸门 / 无轮次上限 / 无并发上限 / **工具返回无体量上限、loop 侧无超长落盘兜底** / 工具返回未做注入筛查 / 安全检查 fail-open / 无步骤级用例 / 无回归样本 / 系统提示词上次确认日期不明。

## 五、各步骤怎么走

| 步骤 | 增量场景的走法 |
|---|---|
| 0 意图与边界 | 只写本次新增能力的意图与边界 |
| 1 场景分类 | 跳过（写进继承声明），但要判一遍 §一 的退回信号 |
| 2 设计 | 只做增量设计 |
| 2.5 逐维检查 | 照走 D1–D11，范围限于新增能力。已在 §二 声明继承且本次不动的维度，标 `N/A` 并注明继承来源——**不是跳过不写**。各维度在增量场景的重点见下表 |
| 3 用户核对 | 只问 `../delivery/design-doc-template.md` §一 的这六批——「授权与安全边界」「工具返回体量」「提示词对齐」「信息缺口确认」「注意力与分层」「测试与评测」——加缺口清单；已继承的批次跳过。**按标题名定位，不要按编号**：批次编号会随模板版本变化 |
| 4 实现或比对 | 照走，新增节点必须有可单独运行的用例；新增工具实跑极端返回用例并记录实测 token 数 |

各维度在增量场景的重点：

| 维度 | 增量场景看什么 |
|---|---|
| D1 信息完备性 | 只查新增能力涉及的 Agent，判断它够不够判 |
| D2 输入侧注意力 | 新增内容给既有 Agent 的提示词加了多少负担，会不会把原本没触线的 Agent 推过红线 |
| D3 产物侧构造 | 新增能力是否引入了新的长交付物 |
| D4 工具返回体量 | 新增工具逐个按最坏情况估最大返回；平台无落盘兜底时在工具侧自兜底并建极端返回用例 |
| D5 授权与安全 | 新增工具逐个标自主级别、逐个列新引入的不可信输入来源 |
| D6 Loop 与终止 | 本次不改 loop 则继承；但要判新增能力会不会让既有任务多跑几轮而撞上原有上限 |
| D7 可靠性与恢复 | 新增工具是否带副作用；带的话幂等键从哪来，能不能复用平台既有的重试策略 |
| D8 记忆与隐私 | 新增能力是否读写记忆或检索；是的话必须走平台既有的过滤层，不能自建一条旁路 |
| D9 成本与性能 | 新增能力对单次任务成本与延迟的增量 |
| D10 多 Agent | 新增能力若要求派子代理，这已是退回信号（见 §一），不在增量范围内 |
| D11 测试与评测 | 新增节点必须有可单独运行的用例；新增工具的极端返回用例；存量不动 |

产出文档用 `../delivery/design-doc-template.md` §五 的增量骨架，路径与索引规则同新建场景。

## 常见症状

| 症状 | 动作 |
|---|---|
| 增量需求撞上平台已知缺口（无闸门、无用例、返回未筛查） | 能在能力层补的就补，补不了的显式登记为风险并标注影响，交用户裁决；不静默继承（§四） |
| 找不到某项基线的继承来源 | 这不是"继承"而是"未知"，登记进 §四 的平台缺口清单，不要写"沿用现有做法"含糊过去 |
| 新增能力似乎要动编排模式或资源上限 | 这是 §一 的退回信号，退回「新建」入口走完整流程；不确定时按新建走 |

# 排障模式

Agent 行为异常时的定位流程。**入口判定为「排障」时读**——已知有异常、要找根因，不是全面体检（那是 `review-mode.md`）。

核心做法：**先读对话记录，再猜**。而且读的方式有讲究：**先降噪成骨架时间线，从头正序找第一个偏离点，再展开那一处的原文**——绝不从报错处倒着看，也绝不在读记录之前动提示词。

## 一、入口判定

三条命中任一即走排障入口：

1. 已上线或已跑通的 Agent，行为**变了**或**不符合预期**（跑偏、停不下来、该调的工具不调、结论凭空出现、产出被截断、偶发失败）。
2. 用户拿着一次具体的失败运行来问"这是怎么回事"。
3. 评审或实现验证过程中撞见一次实际异常，需要先定性再决定要不要改。

与其它入口的分界：

| 入口 | 已知什么 | 要产出什么 |
|---|---|---|
| **排障** | 已知有一次具体异常 | 这一次异常的根因 + 归属层 + 处置 |
| 评审 | 不知道有没有问题 | 全维度体检清单 |
| 新建 / 增量 | 还没有实现 | 设计方案 |

排障**不走**完整的步骤 0→4，不需要先独立设计（那是评审的前置，用于避免锚定；排障要的恰恰是贴着现场看）。定位完成后按 §七 收口，只在根因指向架构缺陷时才升级为评审或重新设计。

## 二、第一动作：拿到对话记录

**对话记录（transcript / trace）是排障的唯一一手证据。** 它记录了模型每一轮实际看到什么、实际输出什么、环境实际返回什么——其余材料（代码、提示词模板、配置、用户复述）都是**主张**，只说明"本应如此"，不说明"当时如此"。

要拿到的最小集合，按优先级：

1. **实际发往模型的每一轮请求**：system 段全文、messages 序列、tools 清单、模型 ID 与采样参数。
2. **模型每一轮的原始返回**：文本、thinking、tool_calls、`stop_reason` / `finish_reason`、`usage`。
3. **每次工具调用的入参与返回**：含错误码、耗时、返回体量。
4. 轮次编号与时间戳。

**这是 harness 侧记录，不是应用日志。** 应用日志记的是"我们以为发生了什么"，transcript 记的是"模型收到并据以决策的是什么"——两者对不上本身就是一类高频根因（§五 表中第一行）。

**拿不到记录时，第一动作是把记录补上，不是继续猜。** 明确告诉用户：现在做的任何归因都是猜测，成本高、可证伪性差。补记录的最小实现是在 LLM 调用出入口把完整 request/response 落盘（含 tools 与 stop_reason，注意脱敏），然后复现一次。

同时把这件事**当作 P0 级缺陷单独置顶**（写法同 SKILL.md 约束 15）：**没有可读的对话记录，是可观测性缺陷本身**。它之所以够格与 D5/D7/D8 的红线并列，是因为它让这个系统的**每一个**维度都失去可核对的证据——每一次异常都只能靠猜。

复现前先定性：**必现还是偶发**。必现的固定输入重跑一次拿新记录；偶发的先捞出足量的失败样本与成功样本，成对比较（§六 第 3 条）——偶发问题的根因几乎不在提示词里。

## 三、降噪：骨架时间线

**不要把原始 transcript 整份读进上下文。** 一次真实的 agent 运行动辄几万到几十万 token，硬读的结果是上下文被打满，然后你被迫抽样——而抽样恰恰会漏掉第一偏离点。这与 D4 是同一条原则：**大体量内容先落盘、只把骨架带进上下文，需要哪一段再按索引取**。

降噪规则：

| 保留 | 筛掉 |
|---|---|
| 轮次编号、角色（system / user / assistant / tool）、时间戳 | thinking 全文 |
| **工具名**、调用序号、成功或失败、错误码 | 工具入参全文 |
| 每段内容的**体量**（token 或字符数） | 工具返回全文 |
| `stop_reason` / `finish_reason`、模型 ID | assistant 文本正文（只留首尾各一两行） |
| 参数的**指纹**（如入参的哈希或关键字段值，用于识别"同参重复"） | |

**thinking 与工具返回一律筛掉正文、但保留名字与体量**——名字给你时间线，体量给你 D2/D4 的判据（哪一轮把上下文吃掉了），正文等定位到嫌疑轮次再单独取。

骨架长这样，一屏能扫完：

```
#08 assistant  think 1.2k → tool read_file(a1b2)          #09 tool ok 340t
#10 assistant  think 0.9k → tool read_file(a1b2)  ← 同名同参  #11 tool ok 340t
#12 assistant  think 1.1k → tool read_file(a1b2)  ← 同名同参  #13 tool ok 340t
#14 assistant  think 3.4k → tool search_db(9f3c)          #15 tool ERR 429 timeout
#16 assistant  text 120t   stop=max_tokens
```

生成方式**因 harness 而异，不存在通用脚本**——各家 transcript 的字段名、嵌套方式、thinking 的承载位置都不同。写一段一次性脚本即可，字段名对着实际文件改：

```python
import json, hashlib
for i, line in enumerate(open("transcript.jsonl")):
    m = json.loads(line)                      # 字段名按你的 harness 改
    role, parts = m.get("role"), m.get("content") or []
    bits = []
    for p in parts if isinstance(parts, list) else []:
        t = p.get("type")
        if t == "thinking":
            bits.append(f"think {len(p.get('thinking',''))//4}t")
        elif t == "tool_use":
            fp = hashlib.md5(json.dumps(p.get("input"), sort_keys=True).encode()).hexdigest()[:4]
            bits.append(f"tool {p.get('name')}({fp})")
        elif t == "tool_result":
            bits.append(f"ret {len(json.dumps(p.get('content')))//4}t "
                        f"{'ERR' if p.get('is_error') else 'ok'}")
        elif t == "text":
            bits.append(f"text {len(p.get('text',''))//4}t")
    print(f"#{i:03d} {role:9s} " + " → ".join(bits) + f"  stop={m.get('stop_reason','')}")
```

入参指纹（上面的 `fp`）是这一步最有价值的派生字段：**它让"同一个工具用同一组参数被反复调用"在骨架上一眼可见**——这是无进展打转最典型的签名，看工具名是看不出来的。

规模再大时（几百轮、多个子 Agent）按 SKILL.md §步骤 2.5 的规模分流处理：每条链路派一个子代理生成骨架并回报，你只做跨链路对齐。

## 四、定位第一偏离点

**从头正序读骨架，找第一处与预期不符的地方。** 不要从报错处倒着看。

原因：Agent 的错误会沿轮次被搬运和放大——第 5 轮读错了一个字段，第 30 轮才表现为一个自信的错误结论；报错的那一轮往往只是最后一块倒下的骨牌。倒着看会把你引向症状点的代码，而那里通常没有 bug。

**第一偏离点** = 从这一轮起，实际发生的事与"信息正确、规则正确时本应发生的事"分岔。把它归入三类之一：

| 类型 | 判据 | 一句话 |
|---|---|---|
| **输入偏离** | 这一轮模型**实际看到**的内容本身就是错的、缺的、被截断或被改过 | 它判错了，但换谁都会判错 |
| **决策偏离** | 输入正确、完整，模型仍选错工具 / 传错参数 / 下错判断 | 信息给到了，判断没做对 |
| **执行偏离** | 决策正确，但动作没生效、生效了结果没回来、或重复生效 | 想对了，做的时候出了事 |

**判断输入偏离必须看那一轮实际发出的 request，不能看提示词模板、配置文件或设计文档。** 模板正确 ≠ 拼装后正确：变量没渲染、上下文被裁剪策略切掉、消息角色错位、工具没注册进 tools 清单、上游 handoff 少传一个字段——这些在模板里全都看不见，只在 request 里看得见。**这一条是 harness 排障最常被跳过、也最常一跳过就白忙半天的一步。**

**三类的归属截然不同**：输入偏离与执行偏离通常是 harness 或外部程序的工程问题，改提示词无效；只有决策偏离才可能真的指向提示词与信息供给（D1/D2）。**多数被归因为"模型不听话"的案例，实际是输入偏离。**

## 五、分层归因

拿到第一偏离点与它的类型后，按下表定归属层、取判别证据。**每一行的"判别证据"都是可取到的具体东西，不是推断。**

| 骨架上的现象 | 优先怀疑 | 判别证据 | 层 | 相关维度 |
|---|---|---|---|---|
| 模型引用了不存在的内容 / 忘记前面说过的事 | 上下文裁剪或压缩把原文丢了 | 查该轮 request 的 messages 里被引用的原文还在不在 | harness | D2 D9 |
| 该调的工具从没被调用过 | 工具未注册 / 描述不足 / 未授权 | 查该轮 request 实际下发的 `tools` 清单——**不是查配置文件** | harness | D2 D5 |
| 同一工具同参数连续重复调用 | 返回没有真正携带结果，或无进展检测缺失 | 展开该轮返回体：是否为空、错误被吞成了空成功、缺模型要的字段 | harness / 外部程序 | D6 D7 |
| 轮次戛然而止、没有最终答复 | 输出被截断 | `stop_reason=max_tokens` + `usage`；再看应用层有没有把截断当成正常完成 | 供应商 / harness | D3 D6 |
| 单轮之后行为整体退化 | 某次工具返回吃掉了上下文预算 | 骨架上该轮的返回体量；与窗口上限比 | harness | D4 |
| 系统提示词里出现了用户数据或工具返回内容 | 拼装时把不可信内容拼进了系统指令位 | 该轮 request 的 system 段全文 | harness | **D5（P0）** |
| Agent 拿到了不该看到的数据 | 检索未在入上下文前按身份过滤，或过滤条件来自模型入参 | 该轮工具入参里有没有 `tenant_id` 之类由模型自己传的过滤键 | harness | **D8（P0）** |
| 代码没动，行为在某个时间点后整体变化 | 供应商侧模型版本、默认参数或工具调用格式变更 | 对比该时间点前后同类记录的模型 ID、`usage` 形态、tool_call 结构 | 供应商 | — |
| 偶发失败，重跑就好 | 限流、超时、并发竞争 | 时间戳间隔 + 429/5xx；是否共享写入无并发控制 | 供应商 / 外部程序 | D7 D10 |
| 报错来自工具内部 | MCP server / 业务 API / DB / 沙箱 | 展开返回体取**原始错误码与 request id**，去外部程序侧日志对齐 | 外部程序 | D7 |
| 动作声称完成但环境没变 | 幂等键、事务或异步投递问题 | 环境状态实查 + 外部程序侧的写入记录 | 外部程序 | **D7** |
| 输入完整正确，模型仍反复判错同一类情况 | 规则确实没给到，或提示词自相矛盾 | 系统提示词中该判断依据的规则原文；有没有两处冲突表述 | 设计 | D1 D2 |

四个层的意思：

- **harness**：你自己写的 agent 工程——提示词拼装、上下文管理与裁剪、工具注册与授权、loop 控制、消息构造、返回处理。**排障中命中率最高的一层。**
- **供应商**：模型侧——版本、限流、截断、格式变更、参数默认值。
- **外部程序**：harness 对接的东西——MCP server、业务 API、数据库、沙箱、消息队列。
- **设计**：提示词与信息供给本身的问题。**只有排除了前三层，才轮到它。**

顺序有讲究：**先查 harness 与外部程序，最后才查设计。** 反过来做（一上来就读提示词找毛病）几乎总能"找到点什么"，然后你改了提示词、异常碰巧不复现，根因被埋进去，下次换个输入原样复发。

## 六、展开验证

定位到嫌疑点后才展开原文：那一轮的 request 全文、thinking 全文、工具入参与返回全文。此时读的量很小，也读得起。

四条纪律：

1. **一次只改一个变量。** 同时改提示词和裁剪策略，异常消失了你也不知道是哪个起的作用——而且很可能两个都改错了。
2. **验证要能证伪。** "改完跑了一次没复现"对偶发问题毫无说服力。必现问题：改前改后各跑一次，前必现、后必不现。偶发问题：先算基线发生率，再比改后发生率，样本量不足就说样本量不足。
3. **成对比较。** 手上有成功样本时，把失败样本与成功样本的骨架并排看——差异点通常只有一两处，比单看失败样本快一个量级。
4. **不在生产环境做验证性改动。** 需要实跑验证的（改小上限撞停、重复投递验幂等、越权检索验隔离）按 `review-mode.md` §三 的规矩来：取得授权、在测试或预发环境用合成数据。

## 七、收口

定位完成后**必须做完这四件事**，缺一件这次排障就白做了一半：

1. **归因写清楚层与证据**：哪一轮、哪一类偏离、归到哪一层、判别证据是什么。含糊的"可能是上下文的问题"不算结论。
2. **映射回维度**：根因落在 D1–D11 的哪一维（§五 表最后一列），按该维度的 reference 给处置。根因是"这一维压根没做"时，说明它不是一次偶然故障，而是架构缺陷——**升级为评审或重新设计，不要就地打补丁**。
3. **补一条回归用例**（D11）：把这次的关键输入与骨架片段固化成夹具，能程序断言的一律程序断言。修完不补用例，等于买了个下次原样复发的期权。
4. **如实报告边界**：哪些结论有一手证据、哪些是推断、哪些因为拿不到记录仍是 `unknown`。**拿不到证据是 `unknown`，不是 `fail`**——同 `review-mode.md` §三。

## 八、纪律与禁止

- **绝对禁止在读过对话记录之前修改提示词。** 这是排障中最常见的错误止血方式：它掩盖问题、无法证伪，而且会让下一次同样的异常更难查——因为提示词里多了一句谁也说不清为什么在的话。
- **绝对禁止把"模型不听话"当结论。** 它是待查的现象，不是根因。先按 §四 判偏离类型；多数这类案例最后落在输入偏离。
- **绝对禁止拿应用日志代替 transcript 下结论。** 应用日志记的是"我们以为发生了什么"。
- **绝对禁止用关键词搜索直接下判定。** 在 transcript 里 grep 一个词用于**缩小范围**是对的，用它断言"记录里没有 X 所以没做 X"是错的——同 SKILL.md §程序化与启发式的边界。
- **不在报告里贴出记录原文中的凭据与客户数据**，只写轮次位置与字段名，值一律脱敏。
- **不为了复现而在生产环境重放有副作用的动作。**

## 常见症状

| 症状 | 动作 |
|---|---|
| 拿不到对话记录 | 第一动作是把记录补上并复现，不是继续猜；同时按 P0 登记可观测性缺陷（§二） |
| transcript 太大，读不动 | 先降噪成骨架时间线再读，需要哪一轮再取原文；不要抽样（§三） |
| 从报错点倒着查，查到的代码没毛病 | 改从头正序找第一偏离点——报错轮通常只是末端症状（§四） |
| 提示词模板看着没问题，行为却不对 | 看那一轮**实际发出的 request**，不是模板：变量未渲染、上下文被裁剪、工具没进 tools 清单都只在 request 里可见（§四） |
| 同一工具同参数反复调用 | 展开返回体看是不是空成功或吞了错误；再查 loop 侧有没有无进展检测（D6/D7） |
| 代码没动但行为变了 | 优先查供应商侧变更：模型 ID、默认参数、tool_call 格式（§五） |
| 偶发、重跑就好 | 捞成功与失败样本成对比较；查限流、超时、并发写入（§六 第 3 条） |
| 改了提示词就不复现了 | 不算定位。回到 §四 补上第一偏离点的证据，否则根因只是被盖住了 |
| 根因是某个维度压根没做 | 这是架构缺陷不是偶发故障，升级为评审或重新设计，不要就地打补丁（§七 第 2 条） |

# 评审模式

评审已有 Agentic 实现时的完整流程与证据要求。新建场景不读此文件。

入口判定为「评审」时读。**它就是步骤 4 的「有实现」分支**——前置条件是已走完步骤 0→3 得出你自己的独立设计。

## 一、前置：先独立设计

先完整走 SKILL.md 步骤 0→3，得出**你自己的独立设计**，再看现有实现的细节。

原因：先读代码与提示词会把你锚定在既有结构上，场景选型层面的错误（本该是纯程序却做成了工作流、本该拆父子却挤在一个 Agent 里）从此看不见——这类错误的改造成本最高，也最值得在评审中抓出来。

允许在前置阶段了解的：系统要解决什么业务问题、输入输出形态、用户是谁。不看：具体提示词内容、Agent 划分、工具清单。

## 二、判定审计模式

**按手上实际拿到的证据判定，取证据支持的最深一档，并在报告开头声明。**

| 模式 | 拿到了什么 | 能下什么结论 |
|---|---|---|
| **设计评审** | 只有架构文档、流程图、提示词、schema | 判断设计是否自洽、选型是否合理。**所有实现层面的断言标 `unknown`** |
| **实现评审** | 可执行代码、配置、提示词、工具定义、测试 | 判断实现是否与设计一致、控制是否真的存在。可跑安全的本地检查 |
| **上线就绪评审** | 上述 + 真实或回放的运行证据、安全控制、回滚、可观测、延迟与成本数据 | 判断能不能上生产 |

两条纪律：

- **设计稿不因为"没有代码"而扣分**——它本来就还没到那一步。
- **但也不能给设计稿下"可以上线"的结论**。没有实现证据就没有实现结论。

**证据层级**（判定时按这个顺序取信）：

1. 环境状态、授权日志、对抗测试结果 —— 完成证据
2. 服务端代码与策略测试 —— 实现证据
3. 工具 schema 与运行时配置 —— 实现证据
4. 提示词与文档 —— **只是主张**

设计文档说"会做鉴权"是主张；代码里有鉴权是实现证据；越权测试拿不到数据才是完成证据。**冒烟测试、能登录、装得上、跑通一次，都只证明可达，不证明可靠。**

## 三、逐维评估与证据状态

按 SKILL.md §步骤 2.5 的 **D1–D11 维度矩阵**逐维评估——与设计侧同一张表，不另起一套标准。每维给出：

**证据状态**（五选一）：

| 状态 | 含义 |
|---|---|
| `pass` | 被检视过的证据直接支持 |
| `partial` | 已实现但明显不完整，或验证薄弱 |
| `fail` | 与证据矛盾，或该用途下必需却缺失 |
| `unknown` | 未提供证据，或无法验证 |
| `N/A` | 该维度不适用，**必须写明理由** |

**`unknown` 与 `fail` 不能混用**：拿不到证据是 `unknown`（缺的是证据），必需的控制确实不存在是 `fail`（缺的是控制）。把 `unknown` 写成 `fail` 会制造假问题，把 `fail` 写成 `unknown` 会放过真问题。

**每维的产出**：`维度 → 证据状态 → 问题项（各带证据与影响）→ 处置建议 → 改造成本`。

### 交互方式：两段式与非两段式

**D2（注意力）、D3（产物构造）、D9（成本性能）、D10（多 Agent 必要性）走两段式**，不可省略前一段：先带证据呈现问题 → 用户确认这确实是问题 → 才给改进建议。

理由：提示词冗长、场景合并、多派一个 Agent 这类现象，常有用户已知的业务理由（例如刻意合并以省一次调用），未经确认就给建议会变成噪声。

**D1、D4、D5、D6、D7、D8、D11 不走两段式**：无闸门的高影响动作、fail-open 的安全检查、拼进系统指令位置的不可信内容、无任何兜底的超长返回、只靠模型自述的终止条件、不幂等的副作用重试、未做租户过滤的检索、多节点只有端到端测试——这些是客观缺陷不是权衡，带证据直接给出处置建议。用户可以决定不修（记为"用户接受该风险"），但不需要先确认"这算不算问题"。

### 证据必须实测的维度

以下实测**须先取得用户授权，且在测试/预发环境用合成数据进行**。用户不提供环境或不批准时，该维度标 `unknown`，并在结论里写明「补跑哪条测试可定性」（§六 第 4 条）——**不得用代码走查冒充实测，也不得为完成评审而擅自在生产环境执行**。

**D4（工具返回体量）**：按 `../tools/tool-output.md` §五 构造最坏输入实跑一次，用实测 token 数说话。评审里最容易被反驳掉的就是"我觉得它可能会很大"。

**D6（loop 上限）**：把上限调小实跑一次，确认它真的拦得住；只在代码里看到 `MAX_STEPS` 常量不等于它生效了。

**D8（租户隔离）**：以 A 身份实跑一次必然命中 B 数据的检索，确认结果为空。这一条**不接受代码走查代替实测**。

### 规模分流

现有 Agent 数量超过 6 个时，按对象分批派并行子代理：D1/D2/D3/D8 按 **Agent** 分批，D4/D5 按 **工具/MCP 清单**分批，D10 按 **handoff 链路**分批，D11 按**节点**分批。每个子代理回报结构化清单，你只做汇总与跨对象的一致性判断。D5–D9 中涉及全局机制的部分（loop 实现、预算、熔断）由你自己看，不要拆——它们本来就只有一处实现。

## 四、证据要求

每条问题必须带可核对的证据，不接受"提示词有点长""职责不太清晰"这类判断。

| 问题类型 | 必须给出的证据 |
|---|---|
| 提示词过长 | 文件:行范围、字符数、超红线多少 |
| 场景混杂 | 提示词中并存的分支条数及各自位置 |
| 信息给多了 | 首轮内嵌资料的 token 估算、其中多少属于"可能用到" |
| 工具超最小集 | 授权的工具清单、其中哪几个在流程中从未被用到 |
| 用启发式顶替语义判断 | 规则位置、它替代的是哪个判断、有无覆盖率证据与反例集 |
| 长产物一次性生成 | 该节点单次产出量的估算、是否出现过截断或遗漏 |
| 工具返回超长 | 工具名、最坏输入下的**实测**返回 token 数、现有兜底有没有、loop 侧阈值是多少 |
| 超长返回被静默截断 | 截断发生的代码位置、截断后返回里有没有告知总量与获取剩余部分的方式 |
| 中间状态易失 | 哪个关键中间结论只存在于对话历史、压缩后会丢什么 |
| 高影响动作无闸门 | 哪个工具、哪个动作不可逆或高影响、现状由谁把关（"靠提示词提醒"即视为无闸门） |
| 不可信内容进系统指令位 | 拼接发生的代码位置、拼进了哪一段 |
| 安全检查 fail-open | catch / 超时分支的代码位置、该分支放行了什么 |
| 子 Agent 产出被当可信 | 哪条链路、子 Agent 读了哪些不可信来源、父 Agent 采纳前有无筛查 |
| 终止只靠模型自述 | loop 代码位置、完成判定的依据是什么、有没有外部验证 |
| 缺 loop 上限 | 四类上限各有没有、值是多少、撞上限后的返回长什么样 |
| 撞上限静默返回 | 触顶分支的代码位置、返回值里有没有可程序判定的 stop_reason |
| 重试不幂等 | 哪个动作、幂等键从哪来（或没有）、重复投递的实测结果 |
| 无进展未检测 | loop 里有没有重复调用检测、实测转多少轮才停 |
| 检索未做租户过滤 | 过滤发生在检索层还是取回后、过滤条件从哪来（模型传入即视为无隔离）、越权检索的实测结果 |
| 记忆无来源与时效 | 记忆记录的字段清单、缺哪几项、导致哪类更正做不了 |
| 缓存被动态内容打断 | 变动内容在提示词中的位置、实测缓存命中率 |
| 只看均值不看分位 | 现有指标清单、有没有 p95/p99 与超时率 |
| 多 Agent 无必要性论证 | 有没有单 Agent 基线数据、多出来的成本与延迟是多少 |
| handoff 丢失字段 | 实际交接内容、缺 `../multi-agent/multi-agent.md` §三 的哪几项 |
| 评审者不独立 | 评审节点拿到的输入是什么、有没有原始证据 |
| 缺步骤级用例 | 哪些节点没有用例、现有测试只覆盖到哪一层 |
| 评测 Agent 未校准 | 有无人工标注样本、一致率是否测过 |
| 缺安全样本 | 评测集里有无注入 / 越狱 / 有害输出切片、安全标签是否在门禁里 |

证据同时要说明**影响**：这个问题会导致什么行为退化（漏判、跑偏、返工成本、无法定位故障、多花多少钱）。只有现象没有影响的条目，不列入清单。

## 五、矛盾检查

逐维评估完成后、写结论之前**必跑**。成本很低，抓的都是真问题——因为它查的是"两处各自看着都合理，合起来对不上"的地方，而这类问题在逐维检查中天然看不见。

逐条核对：

| 核对 | 典型矛盾 |
|---|---|
| 提示词承诺 vs 工具实际权限与服务端强制 | 提示词说"执行前必须确认"，工具却能直接调用且服务端不校验 |
| 声称完成 vs 工具返回与最终环境状态 | 日志里写"已提交"，环境里查不到这次提交 |
| 记忆与检索范围 vs 租户与保留期边界 | 文档说按租户隔离，检索代码里的过滤条件来自模型入参 |
| 重试逻辑 vs 幂等性与副作用 | 有重试，但被重试的动作会重复扣款 |
| 多 Agent 角色 vs 实际信息流与终止条件 | 图上是"独立评审"，实际评审节点只拿到上游结论 |
| 评测结论 vs 样本量、任务分布与留存证据 | 声称通过率 95%，样本只有 8 条且全是正常路径 |
| 声明的上限 vs 代码里生效的上限 | 文档写 20 轮，代码里是 200，或常量根本没被引用 |

**发现矛盾要如实暴露，不要抹平。** 两处说法不一致本身就是问题——至少说明文档与实现有一处是错的，而使用者不知道该信哪个。

## 六、结论与回填

1. **P0 置顶，不做加权平均。** 触到 SKILL.md §绝对禁止 或 D5/D7/D8 红线的项单独列在结论最前面。**一个 P0 不因为其他维度表现好而降级**，也不写"总体良好但……"这种把阻断项埋进转折句的写法。
2. 声明**审计模式**与本次评审的**边界**（看了什么、没看什么、哪些标 `unknown` 及为什么）。
3. 结论只覆盖**被评估过的任务与环境**，不外推。
4. 给出**能改变结论的最小下一步**：补哪一份证据、跑哪一条测试，就能把某个 `unknown` 变成 `pass` 或 `fail`。
5. 把 1–4 与逐维清单写入设计文档的「与现有实现的差异」一节。

## 七、边界

- **不得径自改动现有实现**。评审的交付物是清单与建议，动手改需要用户明确要求。
- 用户不认可的问题项，标注"用户判定非问题"关闭，不反复申辩。
- 差异过大、改造成本高时，输出清单并标注成本，由用户裁决范围，不擅自缩小或扩大。
- **不做未经批准的外部变更**：不为完成评审而发消息、改生产数据或访问额外的私有数据；§三 的实测须经用户授权并在测试环境进行，未获授权时标 `unknown` 而不是硬跑。
- **不在报告里暴露密钥**：只写位置与类型，值一律脱敏。
- **不声称静态检查证明了运行时安全**。
- **不虚构缺失的架构细节**，列进证据缺口。
- **不要求每个 Agent 都必须有记忆、RAG、规划模块、框架或多 Agent**。缺少一个可选特性不是缺陷。

## 八、扫描器的使用纪律

skill 根目录下的 `../../scripts/scan_agent.py` 可在评审陌生仓库时先跑一遍：

```bash
python3 <skill根目录>/scripts/scan_agent.py <目标路径> --format markdown
```

仅需 Python 3 标准库，无需安装。它产出两类东西：按维度的**证据缺口**（某类信号全仓库零命中）与**风险线索**（疑似凭据、fail-open 分支、危险执行等）。

三条纪律：

1. **只产线索，不产结论。** 它的输出**不得直接写进评审报告**。每一条都要人工读过对应代码，确认成立之后才能升格为 finding，并按 §四 补齐证据。
2. **零命中不等于没做**。它匹配的是关键词，换个命名就漏。报告"零命中"时必须同时给出所用的匹配模式，让人能判断是真没有还是命名不同。
3. **命中不等于做对**。代码里出现 `retry` 不代表退避正确，出现 `tenant_id` 不代表过滤生效。

这三条是 SKILL.md §程序化与启发式的边界 那条原则在评审侧的落地：**启发式用于缩小搜索范围可以，用于下判定不行。**

## 常见症状

| 症状 | 动作 |
|---|---|
| 现有实现与设计差异过大、改造成本高 | 输出差异清单并标注成本，由用户裁决范围，不擅自缩小或扩大（§七） |
| 用户不认可某条问题 | 标注"用户判定非问题"关闭，不反复申辩，也不擅自改动 |
| 某个维度既拿不到证据、也说不清是否必需 | 标 `unknown` 而不是 `fail`，并在结论里给出"补什么证据能定性"（§六 第 4 条） |
| 评审过程中撞见一次真实异常，需要先定性 | 转 `debug-mode.md` 走排障：读该次运行的对话记录、降噪成骨架、找第一偏离点；定位结果再作为该维度的证据回填 |

# Agentic 应用的测试与评测

系统级测试：多步骤、多 Agent 链路的用例设计、非结构化结果的评测、批量自动化评测。单个 Agent 的提示词级实跑测试（触发、行为、分区编辑、注意力）见 `agent-construction.md` §四。

进入工作流步骤 4（实现或比对）时读。

目录：

- §一 三层测试体系
- §二 步骤级单元测试
- §三 非结构化结果的评测 Agent
- §四 评测集与批量自动化评测
- §五 回归与门禁

## 一、三层测试体系

三层的选取判据见 SKILL.md §测试与评测（权威版本）。本节只补充各层的执行要点与相互关系：

- **步骤级单元测试**（§二）是定位能力的来源。它的成本主要在夹具，一次建好长期复用。
- **端到端用例**跑的是真实链路，用来发现步骤级测不出的问题：节点间的格式错配、顺序依赖、并发冲突。它**不能替代步骤级**——前者只告诉你"坏了"，后者才告诉你"哪一步坏了"。Agentic 的错误会沿链路传播，并被下游节点的自由发挥掩盖，端到端通过不等于每一步都对。
- **批量评测集**（§四）测的是稳定性而非正确性：同一份输入跑十次是否都合格、换个模型是否退化。前两层是通过/不通过，这一层是通过率。

三层不是替代关系，是叠加的。规模小的时候只做前两层，上了规模再建第三层。

## 二、步骤级单元测试

每个节点固定三件事：**输入夹具、期望契约、判定方式**。

- **节点是程序** → 常规单元测试，断言精确值。
- **节点是 Agent** → 断言分两类：

  | 断言类型 | 内容 | 判定方 |
  |---|---|---|
  | 结构断言 | 字段齐全、类型正确、枚举值合法、占位符已清、引用的文件/ID 真实存在 | **一律程序断言**，不许人工看 |
  | 语义断言 | 内容是否正确、推理是否成立、是否答非所问 | 评测 Agent，见 §三 |

- **覆盖要求**：每个节点 ≥ 1 典型输入 + 1 边界输入 + 1 异常输入（空 / 格式不符 / 超出枚举范围）。
- **夹具落盘、可重放**：输入固定成文件，不靠临场手敲。
- 每个节点的输入**必须能脱离上游单独构造**。构造不出来，说明信息传递链路定义不清——这本身就是设计缺陷，回到设计文档的「信息传递链路」一节补齐，而不是改成"只能整链跑"。

## 三、非结构化结果的评测 Agent

产出是自然语言、分析、建议、代码这类无法用相等断言判定的内容时，把评测本身做成一个 Agent（LLM-as-judge）。

**怎么建**：

1. 按 `agent-construction.md` §一 六要素写评测 Agent 的系统提示词，角色设定为该领域的评审者。
2. 输出**结构化判定**：通过 / 不通过 + 每条 rubric 的得分 + **证据引用**（指向被测产出的具体位置）。结构化才能被程序聚合。
3. 输入只给：被测产出 + 该步骤的契约 + rubric + 参考答案（有则给）。**不要把上游全部上下文喂给它**——它只判这一步，多余上下文会让它去评价不归它管的事。
4. 评测 Agent 不与被测 Agent 共用提示词；建议换一个模型档位，减少同源盲区（同 SKILL.md §Agent 构建 模型选择）。

**rubric 写法**：把"好"拆成可独立判定的条目，每条给判分锚点——什么算 1 分、什么算 5 分各举一个例子。禁止"是否准确""是否高质量"这类无锚点条目，它们只会让评测 Agent 自由发挥。

一个合格 rubric 的样子（被测产出：客服工单的自动分类与回复草稿）：

| # | 条目 | 1 分锚点 | 5 分锚点 |
|---|---|---|---|
| 1 | 分类正确性 | 类别与工单主诉不符（把退款问题判为物流问题） | 类别与主诉一致，且多主诉工单选中了最紧急的那个 |
| 2 | 事实依据 | 回复中出现工单与知识库都没有的信息（编造订单状态） | 每条事实性陈述都能在工单原文或知识库中定位，并给出出处 |
| 3 | 处置完整性 | 只复述问题，没给下一步 | 给出用户可执行的下一步，且包含所需的单据号/链接/时限 |

对比一下不合格的写法：「回复是否准确、专业、有帮助」——三个形容词，没有任何锚点，两个评测 Agent 会给出两套分数。

**评测 Agent 必须先校准**：拿 5–10 条人工标注过的已知好 / 坏样本喂给它，核对它的判定与人工标注的一致率。不一致的先改 rubric（多半是锚点不清），再改评测 Agent 的提示词。**未经校准的评测 Agent 等于没有测试**——它会稳定地给出看起来很有道理的错误评分。

## 四、评测集与批量自动化评测

用例规模超过人工逐条看的限度，或需要横向对比版本时，建评测集。

**评测集构成**：正常样本 + 边界样本 + **回归样本**（历史上出过错的输入）+ **安全样本**（注入 / 越狱 / 有害输出，见 `safety.md` §五）。每条样本含：输入、期望产出或 rubric、标签（场景 / 难度 / 来源）。

安全样本的期望值写**判定码**（如 `safety_injection_detected`），不写"应该拒绝"——自由文本的期望值没法程序聚合，也没法比较版本。

**评测要求必须写死**：每条样本的判定口径写在样本里，不留给评测方临场发挥——这是 SKILL.md「不得虚构规则」在测试侧的延伸。口径缺失的样本不算有效样本。

**执行方式**：由**程序**或**一个编排型 Agent** 批量调度，负责并发（受已确认的并发上限约束）、重试、汇总；语义判定调用 §三 的评测 Agent。两者的选择判据——样本形态齐整、判定口径固定 → 用程序，便宜且可重放；样本形态不齐、需要运行时决定怎么测（先探查产物结构再挑判定方式）→ 用编排 Agent。无论哪种，产出报告的结构一致：

- 总通过率
- 按标签分组的通过率（哪类场景弱一目了然）
- 失败样本清单，每条带证据与失败归因

**用途**：通过率是版本比较的依据。每次改提示词、换模型、调分区方案都重跑同一套评测集，比较版本间差异——而不是看单条 case "感觉变好了"。

## 五、回归与门禁

- 修复过的每个缺陷，都要沉淀成一条评测集样本，防止复发。
- 提示词或模型有任何变更 → 重跑评测集，比对通过率。退化就回滚，或写明为什么可以接受。加工具、改工具描述同样触发重跑——授权面变了。
- **门禁阈值写进设计文档**（通过率下限、哪些标签不允许失败），不是每次现场议定。**安全标签默认不允许失败**，通过率不适用于它：一条也不能挂。

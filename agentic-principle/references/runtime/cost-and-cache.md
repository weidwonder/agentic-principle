# 成本、性能与缓存

维度 D9。**上规模运行或有明确预算/延迟约束时读**。

一次性的内部工具可以标 `N/A`，但只要满足任一条就适用：会被反复调用、面向多用户、有成本预算、有响应时间要求、要在多个模型或方案之间做取舍。

§五 的**缓存友好布局与压缩保真**是例外——它对**所有多轮场景**都适用，即使不谈成本，因为压缩失真会直接损坏任务正确性。

## 一、计量口径

**只统计 output token 会严重低估成本。** Agentic 场景的成本大头通常在 input：上下文随轮次累积，第 20 轮的单轮 input 可能是第 1 轮的十几倍。

一次任务的成本口径至少覆盖：

| 项 | 容易漏的地方 |
|---|---|
| input token | 每轮都要重发全部历史，**按轮次累加**，不是只算最后一轮 |
| cached input token | 单价不同，要单独计，否则算不出缓存收益 |
| output token | — |
| reasoning token | 有推理模式的模型另算，且通常不便宜 |
| 工具执行成本 | 外部 API 调用费、沙箱运行时长、检索费用 |
| **重试与失败** | 失败的调用照样花钱，**必须计入**，否则失败率一高账就对不上 |
| **子 Agent 展开** | 父子架构下按整棵调用树累计，不是只算父 Agent |

**统计单位是「一次任务」，不是「一次模型调用」。** 用户关心的是"处理一张工单要多少钱"，不是"单次调用多少 token"。

## 二、各级预算

预算至少分三级，各自的超限行为都要写进设计文档：

| 级别 | 防什么 | 超限后 |
|---|---|---|
| **单次任务** | 单个任务失控 | 按 `agent-loop.md` §三 触顶退出，交出进度 |
| **单用户 / 单租户** | 一个用户耗尽全部额度 | 限流或排队，给明确提示 |
| **全局 / 单位时间** | 整体账单失控 | 告警 + 降级，不是等账单出来才发现 |

超预算时是**降级**（换更便宜的模型、减少检索量、跳过可选步骤）还是**拒绝**（明确告知无法完成），要在设计期定，不留给运行时。

## 三、延迟看分位不看均值

均值会被大量快速请求拉低，掩盖掉长尾——而用户感知的正是长尾。

- 至少跟 **p50 / p95 / p99**，以及**超时率**。
- 交互式场景另跟**首字延迟（TTFT）**：用户等待的是第一个字，不是最后一个字。
- 端到端延迟要包含工具执行时间与重试等待，不是只算模型响应时间。
- 父子架构下，并发子 Agent 的墙钟时间取**最慢那条**，不是平均——这是并行方案最容易被高估收益的地方。

## 四、优化必须端到端评估

**降低 token 但降低成功率或增加重试次数的"优化"是回归。**

例：把提示词砍掉一半，单轮 input 降了 40%，但 Agent 因为规则不全开始试错，平均轮次从 6 涨到 11——总成本反而上升，还多了失败率。

因此每一项优化都要同时报四个数：**成本、延迟、成功率、平均轮次**。四个数里任一显著变差，都要说明为什么可以接受。

各项优化之间会互相影响（压缩上下文会打断缓存复用、换小模型会增加重试），**不能分别评估后把收益相加**，必须在同一套评测集上端到端跑一遍（见 `../delivery/testing.md` §四）。

## 五、缓存友好布局与压缩保真

这两条对**所有多轮场景**适用，与是否上规模无关。

### 5.1 缓存友好布局

大多数模型 API 的 prompt cache 按**前缀匹配**生效：从头开始逐 token 比对，遇到第一个不同就整段失效。因此：

| 位置 | 放什么 | 理由 |
|---|---|---|
| 最前 | 系统提示词、工具/MCP 定义、固定的 Skill 内容 | 跨请求完全不变，缓存命中率最高 |
| 中间 | 本次会话的稳定信息（任务目标、已确认的约束） | 一次任务内不变 |
| 最后 | 对话历史增量、工具返回、当前状态 | 每轮都在变，只影响尾部 |

**最典型的反模式：在系统提示词开头注入当前时间戳。** 每次请求前缀都不同，缓存 100% 失效，成本可能翻数倍——而这个时间戳往往根本没被用到。同类反模式还有：把随请求变化的配置、用户 ID、随机 session ID 放在提示词前部；每轮重新排序工具列表；动态增删工具定义。

需要动态信息时，把它**追加到尾部**（作为最新一条消息或状态块），不要插进前缀。

工具清单同理：**保持稳定的工具目录 + 按需加载详细 schema**，胜过每轮根据情况增删工具——后者会让工具定义段落每轮都变，前缀缓存全废。

### 5.2 压缩保真契约

上下文超限要压缩时，**不是"保留最近 N 条"**——最近的往往是琐碎的试错，而决定性的信息在开头。

压缩后必须保留的六类：

1. **决策**：已经定下来的方案与选择理由
2. **约束**：用户明确提出的要求与禁止项
3. **已改产物**：改了哪些文件/记录，改成了什么
4. **验证状态**：哪些已经验证通过、哪些还没验
5. **未解决工作**：待办与已知问题
6. **来源引用**：结论所依据的文件路径、记录 ID、链接

可以压掉的：重复的探查过程、被推翻的中间尝试、冗长的工具原始返回（保留路径与摘要即可）。

**最容易压错的是失败路径**：把"试过 X 方案，因为 Y 失败了"整段摘要掉，模型很快会再试一遍 X。失败结论必须保留，它是最有价值的信息之一。

**滑动窗口式删除是错的**——它按位置删，不按重要性删，必然会删掉开头的约束与决策。

压缩要有触发阈值（如占用达上下文窗口的 70%）且**压缩本身要可验证**：压缩前后跑一遍关键信息断言，确认六类都还在。

## 六、模型路由

按节点职责分配档位（档位表见 `../prompt/agent-construction.md`），但有两条纪律：

- **不要假设"任务看起来简单就能用小模型"**。要在真实任务上验证：小模型省下来的钱，可能被更高的失败率与重试次数吃掉还倒贴。
- **路由决策要可观测**：日志里记录本次用了哪个模型、为什么走这条路由。否则线上出问题时无法区分是路由错了还是模型不行。

## 六之二、一个完整走法（示例）

被建对象：日均 3 万次调用的工单分类 Agent，需要把单次成本降下来。

1. **先量对**（§一）：原有统计只算 output token，账单对不上。补齐口径后发现真实构成是——input 累积 61%、cached input 18%、output 12%、重试与失败调用 9%。**大头在 input，不在 output。**
2. **第一次"优化"**（§四）：把系统提示词从 6000 字符砍到 2800，单轮 input 降 34%。但复跑评测集：成功率从 92% 掉到 81%，平均轮次从 3.1 涨到 5.4 —— **总成本反而涨了 18%**。原因是砍掉的是分类边界规则，Agent 开始来回试探。判定为回归，回滚。
3. **改走下沉**（§四）：规则不删，改放置层级——把只在疑难工单才用到的细则挪进 Skill 文件、提示词留一行索引。成功率保持 92%，平均 input 降 22%。
4. **修缓存**（§5.1）：查缓存命中率只有 7%，排查发现提示词开头拼了 `当前时间：{now}`——每次请求前缀都不同，缓存全废，而这个时间戳全流程根本没被用到。移除后命中率升到 74%，input 成本再降 41%。
5. **加预算**（§二）：单任务成本上限设为典型值的 4 倍，超限走降级（改用中档模型重试一次），仍超则拒绝并告警。
6. **看分位**（§三）：均值延迟 2.1 秒看着很好，p95 是 11 秒、p99 是 34 秒——长尾来自一个没设超时的知识库检索。补超时后 p99 降到 9 秒。
7. **回归**（§七）：把四个数（成本、延迟 p95、成功率、平均轮次）一起写进评测报告，作为后续每次改动的对比基线。

## 七、用例

D9 适用的实现，交付前至少跑通这四条：

1. **成本口径核对**：跑一个典型任务，把实测账单与你的计量代码算出来的数对齐，确认 input 累积、缓存、重试、子 Agent 都算进去了。
2. **撞预算**：把单任务预算调小跑一次，确认按设计的方式降级或拒绝，且用户拿到明确提示。
3. **缓存命中率**：连续跑同类任务，确认缓存命中率符合预期；命中率异常低时排查前缀是否被动态内容污染。
4. **压缩保真**：构造一个必然触发压缩的长任务，压缩后核对六类信息是否都还在，尤其是开头的约束与失败结论。

第 4 条建议做成断言式回归用例——压缩逻辑的退化很难靠肉眼发现，往往表现为"模型最近有点笨"。

## 常见症状

| 症状 | 动作 |
|---|---|
| 账单突然涨了一截，说不清是哪里涨的 | 缺 §一 的完整计量口径。多半漏了 input 累积、重试与失败调用、或子 Agent 展开 |
| 缓存命中率很低 | 查 §5.1：前缀里是否混进了每轮都变的内容（时间戳、session ID、动态增删的工具定义） |
| 压缩之后 Agent 像变笨了，开始重试早就否决过的方案 | 压缩把失败路径摘要掉了。按 §5.2 的六类保真要求重写压缩逻辑，并加断言式回归用例 |
| 换了小模型省了钱，但总账没降 | 按 §四 端到端复算：成功率与平均轮次多半变差了，省下的单价被重试吃掉 |

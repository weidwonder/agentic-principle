# Agent Loop 与终止条件

维度 D6。**自建 agent loop / harness 时读**——即由你的代码来驱动「调模型 → 解析工具调用 → 执行工具 → 把结果喂回去 → 再调模型」这个循环。

用现成 harness（Claude Code、各家 Agent SDK、工作流引擎）时，这一维大部分标 `N/A`，但仍要查两件事：**该 harness 的默认上限是多少、你的任务会不会撞上它**；以及**撞上之后你的业务代码怎么处理**。默认值不写进设计文档，等于把关键参数交给了别人的版本升级。

## 一、终止条件：三种停法

一个 loop 只有三种合法的停法，缺任何一种都是设计缺陷：

| 停法 | 判据 | 常见写错的样子 |
|---|---|---|
| **完成** | 由**可外部验证的条件**判定 | 只看模型有没有说"我完成了" |
| **触顶** | 撞上 §二 的任一上限 | 只设了步数上限，成本没设 |
| **放弃** | 判定为无法完成，带证据退出 | 没有这条，于是无限重试直到触顶 |

**"完成"必须可被外部验证。** 模型说"已经修好了"不是完成证据；文件内容变成了期望状态、测试转绿、接口返回 200、数据库记录出现——这些才是。判定方式按产出形态选：

| 产出形态 | 完成判据 |
|---|---|
| 改文件 | 目标文件存在且内容满足断言（跑一次校验脚本 / diff 非空且能解析） |
| 调外部系统 | 回查该系统的状态，不用调用的返回值当唯一凭证 |
| 结构化数据 | schema 校验通过 + 必填字段齐全 + 占位符已清 |
| 自然语言产出 | 程序断言能查的先查（长度、结构、引用的文件是否真实存在），剩下的交评测 Agent（见 `../delivery/testing.md` §三） |

**最容易漏的一条**：模型可以在没有调用任何工具的情况下声称完成。loop 必须能识别"这一轮没有工具调用，且完成判据不满足"这种状态——它通常意味着模型卡住了，而不是做完了。

## 二、四类上限

四类都要设值，缺一类就有一条失控路径。写进设计文档，不留在代码常量里。

| 上限 | 防什么 | 起步值参考 | 怎么定 |
|---|---|---|---|
| **步数**（loop 轮次） | 来回空转 | 单 Agentic 20–50；工作流单节点 5–15；子 Agent 10–30 | 拿典型任务实测轮次，取 p95 的 2 倍 |
| **时间**（墙钟） | 卡在慢工具或长响应上 | 交互式 2–5 分钟；后台任务按 SLA 定 | 用户能接受的等待时长，不是模型需要的时长 |
| **成本**（token 或钱） | 上下文越滚越大导致费用非线性上涨 | 单任务给定额，按典型任务成本的 3–5 倍 | 见 `cost-and-cache.md` §二 |
| **连续失败** | 同一个错误反复撞 | 3–5 次 | 连续失败与总失败要分开计 |

三条容易搞错的：

- **成本上限不能只算 output token**。上下文随轮次线性增长，第 20 轮的单轮 input 可能是第 1 轮的十几倍，总成本是超线性的。计量口径见 `cost-and-cache.md`。
- **上限要能按任务分级**，不是全局一个值。"回答一个问题"和"重构一个模块"用同一个步数上限，必然一个太松一个太紧。
- **父子架构下上限要向下传递并累计**：父 Agent 的总预算要覆盖所有子 Agent 的开销之和，不能父子各设各的。子 Agent 的预算由父在派发时分配，写进 handoff 契约（见 `../multi-agent/multi-agent.md` §三）。

## 三、撞上限之后

**静默停止是最坏的处理**：调用方拿到一个残缺产物，却不知道它是残缺的。撞上限时必须做完这四件事：

1. **明确标记这是触顶退出**，不是正常完成。返回值里要有可程序判定的字段（如 `stop_reason: "max_steps"`），不是只在日志里写一句。
2. **交出中间产物与进度**：已完成哪几步、当前状态在哪个文件/记录里。
3. **给出可读原因**：撞了哪个上限、当时在做什么、最后一次工具调用是什么。
4. **说明能不能续跑**：能续的给续跑入口（见 §四），不能续的说明为什么。

对照反例：`if steps > MAX: break` 然后把最后一次模型输出当成最终答案返回——调用方完全无从分辨这是想清楚了还是被砍断了。

**触顶不等于失败**。有些任务本来就该分批做，触顶后带着进度续跑是正常路径。但"触顶"与"完成"必须是两个不同的返回状态，不能合并。

## 四、可中断、可恢复、可取消

任务预计运行超过一两分钟，这三项就都要有：

- **可中断**：外部（用户、超时、上层调度）能让它停下来，且停在一个一致的状态上——不是停在"文件写了一半"。中断信号要在**每轮循环的固定检查点**读取，不要只在工具调用之间读。
- **可恢复**：关键中间状态落在**外部载体**（文件、数据库、任务记录），不是只存在于对话历史里。判据很简单：**进程重启后能不能接着做**。答案是否，就是不可恢复。
- **可取消**：取消要能传播到子 Agent 与外部调用；已经发出去的副作用要么可撤销，要么在取消响应里明确列出"这些已经生效了，取消不掉"。

**最容易写反的是"可恢复"**：很多实现把中间状态存在内存的对象里，看起来有状态管理，进程一挂全丢。设计时直接问：这份状态如果只存在于内存，进程被杀之后会损失什么？损失是"重跑一遍"就接受，损失是"用户填的东西没了"或"钱扣了但记录没写"就不接受。

## 五、异步与事件驱动系统

loop 由消息/事件驱动（而非同步调用）时，另查六项：

| 项 | 查什么 | 出事的样子 |
|---|---|---|
| **幂等** | 同一条消息被投递两次，结果是否相同 | 重复扣款、重复发消息 |
| **去重** | 有没有基于消息 ID 的去重表与保留期 | at-least-once 投递下必然重复 |
| **顺序** | 乱序到达时是否用序号/时间戳纠正 | 用旧状态覆盖了新状态 |
| **陈旧状态** | 处理时是否重新读取权威状态 | 拿着几分钟前的快照做判断 |
| **watchdog** | 卡住的任务由谁发现、多久发现 | 任务永远停在 running |
| **优雅关闭** | 收到关闭信号时在途任务怎么办 | 进程一退，在途任务状态永远悬着 |

幂等的具体做法（幂等键怎么取、去重表怎么设计）见 `reliability.md` §五——它与重试是同一套机制的两面。

## 六、loop 自身的工程职责

自建 loop 意味着下面这些兜底没有人替你做，必须自己实现：

1. **工具返回体量兜底**：执行循环发现返回超阈值即落盘，回给模型的是路径 + 摘要 + 结构索引。这是覆盖面最广的一处实现——一处写好，现有与将来的所有工具（包括改不动的第三方 MCP）都被覆盖。做法见 `../tools/tool-output.md` §二。
2. **shell/bash 通道的统一截断或落盘**：CLI 工具的返回也走这条通道，同样要有上限。
3. **工具调用与结果的配对**：每个 `tool_call` 都要有对应的 `tool_result` 且顺序正确。缺失或错位会让模型看到一段不自洽的历史，行为立刻退化。工具执行抛异常时，**必须回填一条错误结果**，不能不回填。
4. **上下文压缩的触发点与保真要求**：什么时候压、压的时候必须保留什么，见 `cost-and-cache.md` §五。
5. **不可信内容的标注位置**：工具返回在进入上下文时就要带来源标注，而不是指望模型自己分辨。见 `../safety/safety.md` §一。

## 六之二、一个完整走法（示例）

被建对象：一个自动修 CI 失败的 Agent，自建 loop，能改代码、能触发流水线。

1. **定完成判据**（§一）：初稿写的是"Agent 认为修好了就结束"。改为**回查流水线状态**：目标分支最近一次 run 的 conclusion 为 success 才算完成——模型说"应该能过了"不作数。
2. **加"没调工具"的识别**：模型可能直接回一句"已修复"而没动任何文件。loop 判定这一轮无工具调用且完成判据不满足 → 不当成功，回喂一句"完成判据未满足，当前 run 仍为 failure"继续。
3. **定四类上限**（§二）：拿 20 个历史 CI 失败样本实测，修复轮次 p95 是 9 轮 → 步数上限设 20；时间上限 15 分钟（流水线本身要跑 6 分钟）；成本上限按典型任务的 4 倍；连续失败 3 次（同一个测试连挂 3 次说明方向错了）。
4. **定触顶行为**（§三）：撞任一上限时返回 `{stop_reason, attempted_fixes[], last_run_url, branch, resumable: true}`，并把已改动的代码留在分支上不回滚——人接手时能看到它试过什么。
5. **加可恢复**（§四）：每轮把"已试过的修复方案 + 当前失败的测试名"写进任务记录文件。进程被杀后重启，从该文件续跑，不重复试同一个方案。
6. **测**（§七）：把步数上限临时调成 2 跑一次真实失败样本，确认停在第 2 轮、`stop_reason` 正确、分支上的改动还在、续跑时没有重做第 1 轮的方案。

## 七、用例

D6 触线的实现，交付前至少跑通这五条（写成回归用例，不是手工点一遍）：

1. **撞步数上限**：构造一个必然做不完的任务，确认在 `MAX_STEPS` 处停住、返回 `stop_reason` 正确、中间产物可读。
2. **撞成本上限**：把上限调到很小跑一次典型任务，确认成本统计口径正确（含 input 累积）且确实拦住。
3. **假完成**：让模型在不调用工具的情况下直接回答"已完成"，确认完成判据不通过、loop 不把它当成功。
4. **中断与恢复**：任务跑到一半发中断信号，确认停在一致状态；重启后从中间状态续跑，确认不重做已完成的步骤、也不漏掉未完成的。
5. **重复投递**（异步系统）：同一条消息投两次，确认副作用只发生一次。

这五条属于回归用例：改 loop、换模型、调上限值都要重跑。

## 常见症状

| 症状 | 动作 |
|---|---|
| 任务偶尔跑很久停不下来，或成本突然翻十倍 | 缺 §二 的四类上限。补步数 / 时间 / 成本 / 连续失败，并按 §三 定撞线后的返回形态 |
| Agent 报告完成，但产物或环境状态并没有变成期望的样子 | 终止条件依赖了模型自述。按 §一 换成可外部验证的完成判据 |
| 进程重启后任务只能从头再来 | 不可恢复。按 §四 把关键中间状态落到外部载体，判据是"进程重启后能不能接着做" |

# 可靠性与恢复

维度 D7。**有副作用动作或外部依赖时读**——即 Agent 会调用可能失败的外部系统（API、数据库、浏览器、命令行），或会产生改变外部状态的动作。

纯只读、纯本地、纯文本生成的 Agent 可以标 `N/A`；但只要有一个工具会写、会发、会付钱，这一维就适用。

## 一、错误四分类

**先分类，再谈重试。** 不分类就重试，是把"参数写错了"和"网络抖了一下"当同一回事处理——前者重试一万次也一样错。

| 类别 | 典型 | 处理 |
|---|---|---|
| **可重试** | 超时、限流、5xx、连接重置、锁冲突 | 原样重试 + 退避（§二） |
| **可纠正** | 参数校验失败、格式错误、字段缺失、路径不存在 | **改输入再试**，由模型看到结构化错误信息后重新构造调用 |
| **可降级** | 可选依赖不可用、非关键字段取不到 | 带着缺失继续，**并在产物里显式标注缺了什么** |
| **终止** | 鉴权失败、权限不足、余额不足、资源已删除、明确的业务拒绝 | 立即停，交人处理，**不重试** |

**分类要落在工具返回的结构里**，不是靠模型读错误文本猜。工具的错误返回应携带一个可程序判定的类别字段，模型和 loop 都按它决策。做不到分类的错误，默认按"终止"处理——比默认重试安全。

对照反例：把所有异常都 `except: retry(3)`。鉴权失败重试 3 次仍然失败，白等三个退避周期，还可能触发对方的风控。

## 二、重试与退避

只对**可重试**类错误重试。三条硬要求：

- **有界**：次数上限（3–5 次起步）与总时长上限，两个都要有。
- **指数退避 + 抖动**：`delay = base * 2^n * (1 ± jitter)`。没有抖动时，一批并发任务会在同一时刻齐刷刷重试，把刚恢复的下游再打垮一次。
- **尊重服务端信号**：对方返回 `Retry-After` 或限流配额信息时按它来，不用自己的退避曲线。

**可纠正类错误不叫重试，叫改了再试**：必须改变输入或策略。原样重复发送同一个参数错误的请求，无论多少次都是同一个结果——这属于 §三 的无进展。

## 三、无进展检测

Agent 特有的失败形态：不报错，但也不前进。它会一直"很努力地"做同一件事，直到撞上限。

**检测信号**（任一命中即判定为无进展）：

| 信号 | 判据 | 起步阈值 |
|---|---|---|
| **重复调用** | 相同工具名 + 语义等价参数 | 连续 2 次，或窗口内 3 次 |
| **状态未变** | 连续 N 轮后，外部状态与产物均无变化 | 3 轮 |
| **循环往复** | 在两三个状态之间来回切换（改 A 再改回来） | 检测到一个环 |
| **同错重现** | 同一个错误码连续出现 | 3 次 |

参数比对要**归一化后再比**：空白、键顺序、等价路径写法（相对/绝对）都要先规整，否则同一个调用会因为格式差异被判为"不同"。

**命中之后做什么**（按顺序尝试，不是直接放弃）：

1. **告诉模型它在原地打转**，把重复的调用摘要回喂给它——很多时候它只是没意识到。
2. 仍不变 → **强制换策略**：换工具、换参数结构、把任务拆小。
3. 仍不变 → **按"放弃"退出**，带上尝试过的动作清单与最后一次错误，交人处理。

反例：靠在系统提示词里写"请不要重复调用同一个工具"来解决。这是提示词纪律，模型卡住的时候恰恰是它最不遵守纪律的时候——检测必须在 loop 侧用代码做。

## 四、熔断与全局预算

每条恢复路径都要有上界，否则恢复机制本身会变成新的失控源。

- **熔断**：对同一个下游依赖，失败率或连续失败数超阈值即短路，一段时间内直接快速失败，不再发请求。半开状态放少量探测请求确认恢复。
- **全局预算**：所有重试、所有恢复动作、所有子 Agent 的开销共用一个总预算，不是每条路径各自计数。**这是最容易漏的一条**：单条路径重试 3 次看着很克制，5 个工具 × 3 次重试 × 3 层子 Agent，实际放大到几十倍。
- 预算耗尽的行为与 `agent-loop.md` §三 一致：明确标记、交出进度、给可读原因。

## 五、幂等与副作用

**重试只有在副作用幂等或可对账时才是正确性特性**，否则它是重复扣款的生成器。

对每一个会改变外部状态的动作，逐个回答：

| 问题 | 不通过的表现 |
|---|---|
| 幂等键从哪来？ | 用随机数或时间戳当键——重试时键变了，等于没有 |
| 键在哪一层生效？ | 只在客户端去重，服务端仍会重复执行 |
| 键保留多久？ | 短于最大重试窗口，等于窗口外失效 |
| 网络超时但对方其实成功了，怎么办？ | 直接重试；正确做法是先按幂等键查询结果 |
| 不支持幂等的接口怎么办？ | 硬重试；正确做法是先查询状态再决定是否补发 |

**幂等键必须由业务语义决定**：同一笔退款的键应该在重试之间保持不变，通常取「业务实体 ID + 操作类型 + 请求批次」的组合，而不是每次调用现生成一个。

**动作执行完要回查后置状态**。工具返回 200 只说明请求被接受，不等于状态已经变成期望的样子。高影响动作（见 `../safety/safety.md`）必须回查确认，且这个确认要独立于执行本身的返回值。

## 六、部分失败的回滚与对账

多步动作做到一半失败，会留下一个中间状态。三种处理，按可行性选：

| 处理 | 适用 | 要求 |
|---|---|---|
| **事务回滚** | 同一个事务边界内 | 全部步骤都在这个边界内，否则回滚不彻底 |
| **补偿动作** | 跨系统、不可回滚 | 每个正向动作都要有对应的补偿动作，且补偿本身也要幂等 |
| **对账** | 补偿也做不了（消息已发出、款已划走） | 记录不一致、告警、交人处理，**不假装成功** |

**绝不能做的是"隐藏部分状态"**：既不回滚也不上报，让系统停在一个没人知道的中间态。下一次运行会基于这个脏状态继续，故障从此难以定位。

## 七、降级与升级

- **降级**：非关键依赖不可用时带着缺失继续，但**必须在产物里显式标注哪部分是缺的**。悄悄少一块的产物比明确报错更危险——下游会当完整的用。
- **升级（escalation）**：判定为无法完成时交给人，交出去的东西要够用：做过哪些尝试、每次的错误、当前状态在哪、建议的下一步。只发一句"任务失败"等于把排查成本全推给人。

## 七之二、一个完整走法（示例）

被建对象：客服 Agent 的 `refund.create` 工具（发起退款，有副作用、不可逆）。

1. **分类**（§一）：把该工具可能返回的错误逐个归档——支付网关超时 → 可重试；金额格式错、订单号不存在 → 可纠正；风控拒绝、余额不足 → 终止。工具返回体加一个 `error_class` 字段，让 loop 和模型都按它决策，而不是让模型读错误文本猜。
2. **判重试**（§二）：只有"可重试"那一类进重试路径，3 次上限，退避 `1s → 2s → 4s` 各带 ±20% 抖动。可纠正类不进重试——它必须把结构化错误回给模型，由模型改参数后重新发起。
3. **查幂等**（§五）：现状用 `uuid4()` 现生成幂等键 → **重试时键变了，等于没有幂等**。改为 `订单号 + "refund" + 本次工单ID` 的组合，重试之间保持不变；服务端按该键去重，保留期 7 天（覆盖最大重试窗口）。
4. **处理"超时但其实成功了"**（§五）：网关超时不直接重发，先按幂等键查一次退款状态；已成功则直接返回成功，未创建才重发。
5. **加无进展检测**（§三）：Agent 曾出现过反复对同一订单发起退款、每次都被风控拒的情况。loop 侧加检测：相同工具 + 语义等价参数连续 2 次 → 回喂重复调用摘要；仍不变则按"放弃"退出，带上尝试清单转人工。
6. **对账**（§六）：退款已发起但工单状态更新失败时，既不回滚（钱已经走了）也不假装成功 —— 写入不一致记录并告警，交人处理。
7. **测**（§八）：注入超时确认走重试；注入风控拒绝确认**不重试**；同一退款请求投递两次确认只扣一次款；构造反复被拒场景确认无进展检测在第 2 次触发。

## 八、用例

D7 触线的实现，交付前至少跑通这六条（用故障注入，不是等它自然发生）：

1. **注入超时**：确认按可重试处理、退避曲线正确、次数到顶后按"放弃"退出而非静默继续。
2. **注入鉴权失败**：确认按终止处理，**没有重试**。
3. **注入参数错误**：确认错误信息结构化返回给模型，模型改了参数再试，而不是原样重发。
4. **重复投递**：同一个有副作用的动作触发两次，确认最终只生效一次（幂等键起作用）。
5. **超时但实际成功**：让调用超时而下游其实已执行，确认恢复逻辑先查询状态而不是直接重发。
6. **无进展**：构造一个会让模型反复调用同一工具的场景，确认检测触发、干预生效、最终按放弃退出并交出尝试清单。

这六条属于回归用例：改工具、改重试参数、换模型都要重跑。故障注入的夹具要落盘可重放，不靠临时改代码模拟。

## 常见症状

| 症状 | 动作 |
|---|---|
| Agent 反复调用同一个工具、同样的参数，任务却没进展 | 这是 §三 的无进展检测未实现。要在 loop 侧用代码做，不要靠加提示词"请不要重复调用"解决 |
| 重试之后出现重复扣款、重复发送、重复提交 | 缺 §五 的幂等设计。先补幂等键再谈重试——没有幂等键的副作用动作不该自动重试 |
| 同一个错误一直重试到耗尽预算 | 缺 §一 的错误分类。鉴权失败、权限不足、余额不足属于终止类，重试多少次都一样 |

## 一、该不该做成工具

**能程序化的过程尽量程序化**，但"能程序化"指的是**规则确定**的过程：格式转换、字段映射、数值计算、状态机流转、权限判定、计数与硬上限。

**靠关键词、正则、阈值猜语义意图的不算**——那是把语义判断伪装成程序，详见 §八。

程序不能覆盖 100% 场景时，拆成「程序做确定部分 + Agent 做语义部分」，而不是靠堆启发式规则把覆盖率硬补到 100%。

## 二、封装形态选择

| 条件 | 优先形态 | 理由 |
|---|---|---|
| bash/shell **可用** | **Skill（CLI）** | 复用 shell 通道的统一兜底，易迁移，不占工具槽位 |
| bash/shell **不可用** | **MCP / tools** | 没有别的通道 |
| 需要独立的权限控制、审计、参数约束 | **专用工具** | 通用执行器上做不了细粒度授权 |
| 灵活性价值高且风险可控 | **通用工具** | 一个能干很多事，胜过十个各干一点 |

复杂的流程、方法、经验，为了可复用应尽量集成进 **Skill**，便于迁移和加载。Agent 需读取但不经提示词传递的内容，用 **markdown 或 json** 存储。

## 三、工具集的粒度与规模

**用尽可能少的工具完成尽可能多的工作**，同时不引入冗余 token 消耗。

- **按 Agent 的目标切分，不按后端接口切分。** 后端有 30 个 endpoint 不代表要给 30 个工具——Agent 关心的是"查到这个用户的订单状态"，不是"依次调用三个接口再自己拼"。
- **初始工具集要小到能理解、全到能完成任务。** 从 `../prompt/agent-construction.md` §三 的最小能力集起步，缺什么补什么，不要"先给全再收"。
- **读、写、需审批、有外部影响的工具要能被区分**——从命名或分组上就能看出来。混在一起时，授权评估和自主级别标注都会出错。
- **工具目录大了要支持渐进披露**：给一个简短的工具清单 + 一个按需取详细 schema 的入口，而不是把所有 schema 全量塞进每次请求。这同时是缓存友好的（见 `../runtime/cost-and-cache.md` §5.1）。
- **通用执行器（跑任意命令、任意代码）必须在受限环境里运行**：限定可执行范围、文件系统范围、网络出口、资源与时长上限。

## 四、工具描述写什么

工具描述是给模型看的提示词，适用 SKILL.md §提示词质量 的全部要求。

必写：

| 项 | 说明 |
|---|---|
| **什么时候用** | 触发场景，写具体 |
| **什么时候不要用** | 与相邻工具的分界线。**最常被整项遗漏**，也是工具选错的首要原因 |
| **入参含义** | 每个参数是什么、取值范围、必填还是可选 |
| **隐式规则** | 格式约定、互斥参数、单位、默认值来源——**必须显式写出并举最简例子** |
| **返回结构** | 正常与错误两种形态各是什么样，不必逐字段详述 |
| **副作用** | 会改变什么外部状态；无副作用的也要说明是只读 |
| **成本与延迟** | 慢或贵的工具要写明量级，否则模型会毫无顾忌地反复调用 |
| **注意事项** | 有就必须写 |

**一致性要求**：工具初次构建或修改后，**必须复核描述是否反映了最新的入参与各参数含义**。描述与实现不一致，比没有描述更糟——模型会按描述构造调用，然后拿到看不懂的错误。

## 五、防呆设计

**在接口形状上让误用不可能发生，胜过在描述里叮嘱。**

- 只接受**绝对路径**，从根上消除相对路径的歧义。
- 用**互斥的独立参数**替代"某个字段按取值不同含义不同"。
- 用**枚举**替代自由文本，取值集合小的时候尤其如此。
- 危险操作与安全操作**分成不同的工具**，而不是靠一个 `force` 布尔参数区分。
- **格式自然、消除格式化开销**：让 Agent 用最接近自然写法的格式传参，不要逼它做无谓的转义与重排。例：需要传大段代码时用独立字段承载，别要求嵌进 JSON 字符串里逐字符转义——省下的 token 和出错率都很可观。

## 六、工具返回

- 信息不遗漏、低冗余的前提下保持**高可读性**。
- **错误返回必须明确错误原因**，并携带可程序判定的错误类别（可重试 / 可纠正 / 可降级 / 终止，分类见 `../runtime/reliability.md` §一）。只返回一句自然语言的错误，模型只能猜该不该重试。
- **返回体量有上限**：接口设计时就要给出——分页/游标、条数上限、默认摘要 + 明细开关、服务端过滤。不要把"数据多大就返回多大"留给运行时。判据与处置见 `tool-output.md`。
- **返回里夹带的第三方内容是不可信输入**，要带来源标注（见 `../safety/safety.md` §一）。

## 七、服务端才是权威

涉及金额、权限、身份、库存、配额、时效、资格判定时：

- **执行时查询权威状态**，不用模型记住的或上一轮拿到的值。
- **约束在代码里校验**，不靠提示词约定。
- **不要把模型传来的 `expected_*` 之类参数当策略真值**。它可以作为一道校验（对不上就拒绝），但**服务端必须自己重新算一遍**。
- **授权绑定到规范化后的确切操作**上，不是绑到模型的自然语言描述上。
- **执行后回查后置状态**：工具返回成功不等于外部状态已变成期望的样子。高影响动作必须独立确认。

## 八、启发式规则的覆盖率论证

想用关键词表、正则、阈值替代一次语义判断时，先走完这四步，**四步都过且用户确认后才可引入**：

1. **写清规则与它要替代的判断**：这条规则在判什么？不用它的话由谁判？
2. **给覆盖率**：拿一批真实样本（不是自己编的）实测，命中率至少 **75%**。样本量太小算不出可信的覆盖率时，说明证据不足，回到"交给 Agent 判断"。
3. **给反例集**：列出它一定会判错的情形。举不出反例，通常意味着还没想清楚它的边界，不是它真的没有边界。
4. **给兜底**：未覆盖的那部分怎么办——转 Agent 判断 / 转人工 / 显式返回"无法判定"。**兜底不能是"按默认值处理"**，那等于把判错静默化。

覆盖率、反例集、兜底方式三样都要写进设计文档并取得用户确认。

**判断"是不是启发式"的简单方法**：这条规则如果遇到一个它没见过的表述，会怎样？答案是"会安静地给出一个错误答案"，它就是启发式；答案是"会明确报错或走兜底"，它就是确定性规则。

**启发式用于「缩小搜索范围」可以，用于「下判定」不行。** 用正则先筛出可疑位置再逐个读是合理加速；用正则直接判定"这里没有做 X"是错误的。前者的假阳性只浪费时间，后者的假阴性直接写进结论。

## 九、检查清单

新增或修改一个工具时逐条过：

- [ ] 该不该是工具（而不是程序内部逻辑或 Agent 的语义判断）
- [ ] 封装形态按 §二 选定
- [ ] 在该 Agent 的最小能力集之内；读/写/审批/外部影响可区分
- [ ] 描述含：何时用、何时不用、入参含义、隐式规则举例、返回结构、副作用、成本与延迟
- [ ] 描述与最新实现一致（改过实现就要复核描述）
- [ ] 接口形状上做了防呆，不靠描述叮嘱
- [ ] 错误返回带原因与可程序判定的类别
- [ ] 返回体量有上限，最坏情况已按 `tool-output.md` 估算
- [ ] 涉及权限/金额/身份的判定在服务端重算，不信模型传入值
- [ ] 有副作用的动作已标自主级别（`../safety/safety.md`），高影响的有具名闸门
- [ ] 若引入了启发式规则：覆盖率 ≥75%、有反例集、有兜底、已获用户确认

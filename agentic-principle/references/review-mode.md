# 评审模式动作序列

评审已有 Agentic 实现时的完整流程与证据要求。新建场景不读此文件。

入口判定为「评审」时读，先于步骤 4 执行。

目录：

- §一 前置：先独立设计
- §二 六项评估
- §三 证据要求
- §四 边界

## 一、前置：先独立设计

先完整走 SKILL.md 步骤 0→3，得出**你自己的独立设计**，再看现有实现的细节。

原因：先读代码与提示词会把你锚定在既有结构上，场景选型层面的错误（本该是纯程序却做成了工作流、本该拆父子却挤在一个 Agent 里）从此看不见——这类错误的改造成本最高，也最值得在评审中抓出来。

允许在前置阶段了解的：系统要解决什么业务问题、输入输出形态、用户是谁。不看：具体提示词内容、Agent 划分、工具清单。

## 二、六项评估

按序执行，每项独立产出，不要合并成一段笼统结论。

| # | 评估 | 做法 | 产出 |
|---|---|---|---|
| 1 | **架构差异比对** | 独立设计 vs 现状逐项对照：场景选型、Agent 划分、编排模式、信息传递链路 | 差异清单，每项标注：保留现状 / 按设计改 / 需用户裁决 |
| 2 | **注意力负载评估** | 对每个现有 Agent 跑一遍步骤 2.6a 与 2.6b | 问题项 + 证据（见 §三）+ 改进建议（下沉 / 拆分 / 加路由 / 加检查点 / 改模板分区编辑），各标改造成本 |
| 3 | **工具返回体量评估** | 对每个直接进上下文的工具/MCP 跑一遍步骤 2.6c：按最坏情况估最大返回、查有无落盘或分页兜底、查 loop 侧有无统一阈值 | 超线工具清单 + 证据 + 处置建议（loop 落盘 / 工具自兜底），各标改造成本 |
| 4 | **授权与安全边界评估** | 对每个现有 Agent 跑一遍步骤 2.7：逐个工具反推自主级别、找高影响动作有无具名闸门、追不可信内容进了哪些位置、翻安全检查的异常分支是否 fail-open | 问题项 + 证据 + 处置建议，各标改造成本 |
| 5 | **测试完备性评估** | 对照 `testing.md`：每步是否有独立用例、非结构化产出有无评测手段、评测 Agent 是否校准过、有无回归样本、安全切片与门禁阈值 | 缺口清单 + 补齐成本 |
| 6 | **回填** | 把 1–5 的结论写入设计文档的「与现有实现的差异」一节 | 更新后的设计文档 |

第 2 项的交互是**两段式**，不可省略前一段：先带证据呈现问题 → 用户确认这确实是问题 → 才给改进建议。理由：提示词冗长、场景合并这类现象常有用户已知的业务理由（例如刻意合并以省一次调用），未经确认就给建议会变成噪声。

**第 3、4 项不走两段式**：无闸门的高影响动作、fail-open 的安全检查、拼进系统指令位置的不可信内容、无任何兜底的超长返回，是客观缺陷不是权衡，带证据直接给出处置建议。用户可以决定不修（记为"用户接受该风险"），但不需要先确认"这算不算问题"。

第 3 项的证据要**实测**，不接受纯估算下结论：按 `tool-output.md` §五 构造最坏输入实跑一次，用实测 token 数说话——评审里最容易被反驳掉的就是"我觉得它可能会很大"。

现有 Agent 数量超过 6 个时，第 2、4、5 项按 **Agent** 分批派并行子代理执行；第 3 项按 **工具/MCP 清单**分批（它的切分维度是工具，不是 Agent）。每个子代理回报结构化清单，你只做汇总与跨 Agent 的一致性判断。

## 三、证据要求

每条问题必须带可核对的证据，不接受"提示词有点长""职责不太清晰"这类判断。

| 问题类型 | 必须给出的证据 |
|---|---|
| 提示词过长 | 文件:行范围、字符数、超红线多少 |
| 场景混杂 | 提示词中并存的分支条数及各自位置 |
| 信息给多了 | 首轮内嵌资料的 token 估算、其中多少属于"可能用到" |
| 工具超最小集 | 授权的工具清单、其中哪几个在流程中从未被用到 |
| 长产物一次性生成 | 该节点单次产出量的估算、是否出现过截断或遗漏 |
| 工具返回超长 | 工具名、最坏输入下的**实测**返回 token 数、现有兜底（分页 / 上限 / 落盘）有没有、loop 侧阈值是多少 |
| 超长返回被静默截断 | 截断发生的代码位置、截断后返回里有没有告知总量与获取剩余部分的方式 |
| 中间状态易失 | 哪个关键中间结论只存在于对话历史、压缩后会丢什么 |
| 高影响动作无闸门 | 哪个工具、哪个动作不可逆或高影响、现状由谁把关（"靠提示词提醒"即视为无闸门） |
| 不可信内容进系统指令位 | 拼接发生的代码位置、拼进了哪一段（系统提示词 / 工具描述 / SOP / rubric） |
| 安全检查 fail-open | catch / 超时分支的代码位置、该分支放行了什么 |
| 子 Agent 产出被当可信 | 哪条链路、子 Agent 读了哪些不可信来源、父 Agent 采纳前有无筛查 |
| 缺步骤级用例 | 哪些节点没有用例、现有测试只覆盖到哪一层 |
| 评测 Agent 未校准 | 有无人工标注样本、一致率是否测过 |
| 缺安全样本 | 评测集里有无注入 / 越狱 / 有害输出切片、安全标签是否在门禁里 |

证据同时要说明**影响**：这个问题会导致什么行为退化（漏判、跑偏、返工成本、无法定位故障）。只有现象没有影响的条目，不列入清单。

## 四、边界

- **不得径自改动现有实现**。评审的交付物是清单与建议，动手改需要用户明确要求。
- 用户不认可的问题项，标注"用户判定非问题"关闭，不反复申辩。
- 差异过大、改造成本高时，输出清单并标注成本，由用户裁决范围，不擅自缩小或扩大。

# Agentic 设计与编排原则

把一个业务意图，转成一份经过用户确认的 Agentic 方案：场景选型、Agent 与工具边界、提示词、上下文与并发预算、信息传递链路，并据此实现或评审已有实现。

**非目标**：不替代具体业务功能的编码实现；不为"看起来更智能"而把可程序化的流程 Agent 化。

## 三条入口

| 入口 | 触发 | 走法 |
|---|---|---|
| 新建 | 尚无实现，或有实现但要重做架构 | 完整走 §工作流 步骤 0→4 |
| 增量 | 目标平台的场景选型、编排模式、agent loop 已定且本次不动，只新增 skill / 工具 / 配套服务 | 按 `references/incremental.md` 走「继承声明 + 只写增量 + 平台缺口清单」；步骤 1 跳过，2.5 / 2.6a / 2.6b / 2.6c / 2.7 / 3 / 4 照走但范围限于新增能力 |
| 评审 | 已有 Agentic 实现，要 Review | 先走步骤 0→3 得出**独立设计**，再按 `references/review-mode.md` 执行六项评估；禁止一上来就顺着现有实现点评 |

评审时先抛开现有实现独立设计，是为了避免被既有实现锚定，错过场景选型层面的问题。评审的完整动作序列、证据要求与边界都在 `references/review-mode.md`，新建场景不必读。

**增量入口有退回条件**：新增能力若要求改编排模式、提高并发或上下文上限、或让某个 Agent 的职责跨到第 3 个不相干领域，退回「新建」走完整流程。判定细则见 `references/incremental.md` §一。不确定时按新建走——增量入口省的是重复论证，不是省该做的判断。

**接手既有设计文档时**：先看文档 frontmatter 的 `skillVersion`。与本 skill 当前版本（见 frontmatter `metadata.version`）不一致时，**按小节标题名定位，不要按编号**——模板的章节编号会随版本变化，编号对齐会写错位置。差异较大时告知用户，并询问是否按新模板补齐缺失小节。

## 工作流

### 步骤 0 — 理解意图与边界

产出：产品/功能愿景一句话、用户是谁、成功标准、明确的**不做什么**。
信息不足时提问，不要用假设填空。

### 步骤 1 — 场景分类

**先抛开当前实现**，按下表自上而下判定，第一个命中的即是答案：

| 判定问题 | 场景 | 典型例子 |
|---|---|---|
| 流程完全确定，且每一步都不需要语义判断？ | **完全程序过程** | 批量重命名文件；按固定规则生成月度报表 |
| 只需产出文本／建议，不需调用任何工具改变或获取外部状态？ | **单 Agent Chat 应用** | 内部规章问答；文案润色 |
| 步骤次序、分支在**设计期即可穷举**，由程序编排、Agent 只承担其中的语义节点？ | **Agentic 工作流** | 合同审阅流水线：解析 → 并行审阅 → 汇总报告 |
| 任务拆解方式只有**运行时**才知道，或需要并行／上下文隔离？ | **父子 Agentic 应用** | 陌生代码库全量安全审计 |
| 以上都不是：以 Agent 为中心，用户直接对话，Agent 自主调用工具完成任务 | **单 Agentic 应用** | 结对编程助手；数据分析助手 |

相邻场景最容易判错，用下表切边界：

| 相邻场景 | 判为前者 | 判为后者 | 分界线 |
|---|---|---|---|
| 完全程序 vs Agentic 工作流 | Excel 转 CSV | Excel 自由文本备注归类打标 | 是否有一步必须做语义判断 |
| 单 Agent Chat vs 单 Agentic | 解释这段代码的含义 | 找出这段代码的 bug 并改掉 | 是否要读写外部状态 |
| Agentic 工作流 vs 父子 Agentic | 10 份固定格式合同并行审阅 | 审计一个陌生代码库 | 子任务清单是设计期已知，还是运行时探查才知道 |
| 单 Agentic vs 父子 Agentic | 修一个 bug | 同时重构 8 个互不相干的模块 | 是否需要并行 + 上下文隔离 |

**命中「完全程序过程」即退出本 skill**，转常规程序开发。

混合是常态：程序不能覆盖 100% 场景时，不要强行全程序，拆成「程序做确定部分 + Agent 做语义部分」——外层编排确定、个别步骤交给 Agent 处理歧义，是生产系统最常见的真实形态。

### 步骤 2 — 设计

按 §基础原则 + §各场景必确认项 形成设计草案。**此阶段只在会话内形成草案，不落盘、不写实现代码。**

完成判据：草案已能填满 `references/design-doc-template.md` §二 骨架的这几节——场景分类结论、角色与职责、Agent 设计、信息传递链路、上下文与注意力与并发预算（其中注意力负载表在步骤 2.6a 后回填，分区表在 2.6b 后回填，授权与安全边界一节在 2.7 后回填）。填不满的部分即是待确认项，带进步骤 3。

### 步骤 2.5 — 信息完备性检查（强制，由你执行）

这是检查动作，不是提问动作。**逐个 Agent** 检查，不允许抽样：

1. 列出方案中每一个 Agent 节点。
2. 对每个节点，核对它在运行时能拿到的信息（系统提示词 + 首轮 User Prompt + 可读取的 Skill/文件 + 上游传来的数据）**是否足以支撑它要做的每一项业务判断**。
3. 逐条追问：这个判断依据哪条规则？规则写在哪？Agent 读得到吗？边界情况（空输入、格式不符、多义、超出枚举范围）有没有对应规则？
4. 这一步需要实际扫描现有资料（Skill、提示词、文档、样例数据），会花时间和 token，**不要省略、不要用推测替代扫描**。

产出：缺口清单（哪个 Agent、缺哪条规则、影响哪个判断）。缺口带进步骤 3 交用户补充，**不得由你虚构业务规则填补**。

**规模分流**：Agent 数超过 6 个时，按 Agent 分批派并行子代理执行扫描，每个子代理回报结构化缺口清单，你只做汇总与跨 Agent 的一致性判断。子代理数受已确认的并发上限约束。不这样做，扫描会因上下文压力退化成抽样——而抽样正是这一步禁止的。

### 步骤 2.6a — 输入侧注意力负载检查（强制，由你执行）

与步骤 2.5 互为一对：2.5 查"信息够不够"，2.6a/2.6b 查"给的方式对不对、一次给了多少、一次要产出多少"。同样**逐个 Agent**，不允许抽样（规模分流同 2.5）：

1. 估算每个 Agent 首轮的上下文构成：系统提示词字符数、内嵌资料 token 量、工具数量、它要同时应付的场景数。
2. 对照 §注意力与认知负担 的五个抓手与红线逐条核对。
3. 触线项给出处置，四选一：**下沉**（长资料挪进 Skill / 文件，提示词只留索引）／**拆分**（按职责或场景拆成多个 Agent）／**加路由**（前置分类节点，让每个 Agent 只面对一类输入）／**加检查点**（长任务分步，中间状态落外部载体）。

产出：负载清单（哪个 Agent、触了哪条红线、处置方式）。**不得以减负为由删除步骤 2.5 认定为必需的规则**——两者冲突时完备性优先，改用下沉或拆分解决。

### 步骤 2.6b — 产物侧构造检查（强制，由你执行）

逐个 Agent 估算它一次要产出多少内容，对照 §长产物的构造方式 的三条判据：

1. 未命中任何判据 → 按常规产出，本步结束。
2. 命中任一判据 → 改为「程序建模板 → Agent 分区编辑 → 程序校验」，当场定出**分区表**（分区、内容要求、填充者、依赖顺序、校验规则）与模板落盘路径。做法与分区划法见 `references/long-artifact.md`。
3. 分区表在步骤 3 写入设计文档的「信息传递链路」一节。

产出：产物构造清单（哪个交付物、命中哪条判据、分区表）。

### 步骤 2.6c — 工具返回体量检查（强制，由你执行）

2.6a 查"给 Agent 塞了多少"，2.6b 查"让它一次吐多少"，这一步查"**工具塞回来多少**"。逐个工具/MCP，不允许抽样：

1. **划范围**：列出本方案中所有返回**直接进入模型上下文**的工具与 MCP（自建的 + 引入的第三方）。Skill 内 CLI 与外部 CLI 一般不在此列——它们经 shell/bash 通道调用，由通道侧统一兜底，CLI 自身提供 limit / 分页 / 摘要参数即可。**但自建 agent loop 时，通道工具的兜底属于 loop 工程职责，必须实现**。
2. **估最大返回**：对每个工具按**最坏情况输入**估算返回的 token 量（换算与常见超长源见 `references/tool-output.md` §一、§六），不是按典型情况；一轮内会被多次调用的按单轮累计估。
3. **判红线**：估算 > 10k token 即触线，二选一处置——**a. loop 侧统一落盘**（推荐）或 **b. 工具自身兜底**（判据见 §工具返回的体量控制）。
4. **排用例**：**触线（>10k）或落在 5k–10k 灰区的工具必须排极端返回用例**（最大规模输入、实测 token 数、落成回归用例）；估算 <5k 的记录估算值即可，不必实测。走路径 a 的另排一条"超阈值确实触发落盘"的用例，确认兜底没有静默失效。

产出：工具返回体量清单（工具 → 估算最大返回 → 是否触线 → 处置路径 → 兜底实现位置 / 用例编号）。带进步骤 3 交用户确认。

**触线且选路径 b 的，实测结果必须回到用户面前**：实测仍 > 10k 时停下来请用户确认是否改走落盘-读取（路径 a），不得以"一般不会那么大"自行放行。

**2.6a / 2.6b / 2.6c 的处置若改变 Agent 数量、职责边界、模型或工具授权** → 列入步骤 3 交用户确认；纯放置层级的调整直接体现在草案里即可。

### 步骤 2.7 — 授权与安全边界检查（强制，由你执行）

2.5/2.6 管"信息给够没、给法对不对"，这一步管"**允许它做什么、什么内容不能信**"。逐个 Agent、逐个工具，不允许抽样：

1. **标自主级别**：给每个工具/动作标一档（见 §授权与安全边界 的四档表）。
2. **命名审批闸门**：所有 `high-impact-automation` 逐项写清**谁审、在哪一步审、审不过怎么办**，以及闸门的**程序侧实现位置**。写不出来的，视为该项设计未完成，不得带进实现。
3. **列不可信输入**：逐个 Agent 列出运行时会读到的不可信来源（口径见 `references/safety.md` §一 的信任分级表），并定出各自的传入位置与标注方式。
4. **定输出侧检查**：按 `references/safety.md` §三 选出本场景适用的具名检查项与判定码，写明各自的执行者与执行时机。

产出：授权与安全清单（工具 → 自主级别 → 闸门；Agent → 不可信来源；检查项 → 判定码 → 执行点）。带进步骤 3 交用户确认。做法与起步清单见 `references/safety.md`。

单 Agent Chat 场景没有工具，只做第 3、4 项——用户输入本身就是不可信来源，输出侧检查照样要有。

### 步骤 3 — 用户核对

双轨制：

1. **结构化提问**：把关键决策点逐批向用户确认，每批不超过 4 项，优先使用宿主提供的结构化选项提问能力。**完整提问批次见 `references/design-doc-template.md` §一**（权威版本）；各场景的额外差异项见 §各场景必确认项。步骤 2.5 的缺口清单、2.6a 的负载清单、2.6b 的产物构造清单、2.6c 的工具返回体量清单、2.7 的授权与安全清单在此一并交用户。
2. **设计文档终审**：确认后写出设计文档，含流程图，交用户终审。
   - 路径：目标项目 `docs/specs/YYYY-MM-DD-<short-desc>.md`，并同步更新 `docs/index.md`。
   - 模板与流程图写法见 `references/design-doc-template.md`。

**用户明确签字确认后**才进入步骤 4。除非用户明确要求跳过核对——跳过时须把全部关键假设写入设计文档的「确认记录」一节，并一句话告知用户"已按以下假设推进"。

### 步骤 4 — 实现或比对

- **无实现**：按项目既定的分工派发实现。若项目约定由外部编码代理执行，你负责任务书、验收与合并，不亲自编码。实现完成后按 §验证清单 **亲自验证**，并按 `references/agent-construction.md` §四 对每个 Agent 实跑测试（至少 1 个典型任务 + 1 个边界情况；会读不可信内容的 Agent 另加 1 条注入用例；调用大体量数据工具的 Agent 另加 1 条超长返回应对用例），不采信代理的自述。审批闸门要**实跑一遍不通过路径**，确认它真的拦得住、且闸门不可用时 fail-closed。步骤 2.6c 排定的**最大返回用例**要实跑并记录实测 token 数，仍超 10k 的按 2.6c 的规定交用户裁决。多节点场景另按 `references/testing.md` 建**步骤级用例**逐步骤跑通，命中批量判据的建评测集并跑出通过率报告。
- **有实现**：按 `references/review-mode.md` 执行六项评估——架构差异比对 → 注意力负载评估（带证据，先与用户确认成立再给建议）→ 工具返回体量评估（证据须实测，不走两段式）→ 授权与安全边界评估 → 测试完备性评估 → 回填设计文档的「与现有实现的差异」一节。该文件同时给出每类问题的证据要求与不得径自改动实现的边界。

## 基础原则

### 复杂度阶梯

从最简方案起步，只有在可证明改善结果时才升级复杂度。每升一级都要多付延迟、成本与不确定性：

1. 单次 LLM 调用 + 好的提示词
2. ＋检索／in-context 示例
3. ＋工具调用（单 Agentic）
4. ＋程序编排（Agentic 工作流）
5. ＋动态拆解与子代理（父子 Agentic）

与步骤 1 的场景分类互为表里：分类表给出场景的**上限**，这条阶梯要求你在该上限内取**最低可行档**。

### 提示词质量（适用于系统、用户、工具描述、工具返回**全部**提示词）

优先级从高到低：

1. 不遗漏信息、不提供错误信息（最重要）
2. 尽可能低冗余
3. 尽可能结构化
4. 无错别字

### 程序化与工具构建

- 能程序化的过程尽量程序化。但要评估泛化性：程序若不能覆盖 100% 场景，就拆成 Agent + 程序协作，而不是硬做全程序。
- **封装形态选择**：bash/shell 工具**不可用**时，优先 MCP/tools 封装；bash/shell **可用**时，优先 Skill（CLI）封装。
- 工具体系设计：**用尽可能少的工具完成尽可能多的工作**，同时不引入冗余 token 消耗。
- 提示词一致性：工具初次构建或修改后，必须复核其描述是否反映了最新的入参、各参数含义。输出通常只需说明返回结构（正常 + 错误）两种形态，不必逐字段详述。有注意事项必须写进描述。
- 工具返回：信息不遗漏、低冗余的前提下保持高可读性；**错误返回必须明确错误原因**。
- **返回体量有上限**：工具返回直接吃上下文，接口设计时就要给出上限——分页/游标、条数上限、默认摘要 + 明细开关、服务端过滤，不要把"数据多大就返回多大"留给运行时。判据与处置见 §工具返回的体量控制。
- **[重要] 隐式规则显式化**：入参或返回中若存在隐式规则（如格式约定、互斥参数、单位、默认值来源），必须在描述中说明，并用最简洁的语言举例。
- **防呆设计**：在接口形状上让误用不可能发生，胜过在描述里叮嘱。例：只接受绝对路径，从根上消除相对路径的歧义；用互斥的独立参数替代"某个字段按取值不同含义不同"。
- **格式自然、消除格式化开销**：让 Agent 用最接近自然写法的格式传参，不要逼它做无谓的转义与重排。例：需要传大段代码时用独立字段承载，别要求嵌进 JSON 字符串里逐字符转义——省下的 token 和出错率都很可观。

### Agent 构建

- Agent **必须**设置系统提示词，言简意赅、极度精简且不遗漏重要方面。
- **六要素，缺一不可**：角色 → 核心职责 → 处理流程 → 质量标准 → 输出格式 → 边界情况。各要素详略按场景灵活定义，但不得整项缺失。模板、写作细则、工具最小能力集见 `references/agent-construction.md`。
- **角色设定**：从任务出发，思考现实中什么背景、什么经验的人最能完成它，把这个人物角色写进系统提示词。
- **SOP 入提示词的条件**：工作流程完全确定且不变 → 处理流程写死在系统提示词；否则只写框架，细节走上下文管理（Skill / 渐进披露）。
- 单 Agent Chat 场景下，经验与内容尽可能集成进系统提示词（无外部工具可依赖）。
- **增益提示块**：从 `references/system-prompt-blocks.md` 摘取适用块，追加到系统提示词**尾部**。其中「开工前自检」块**必选**（让 Agent 针对本次具体任务再确认一遍流程/标准/格式/边界）；其余按该文件的适用条件矩阵，**只摘条件命中的块**。
- **模型选择**：

  | 节点职责 | 档位 |
  |---|---|
  | 架构判断、跨文件综合、歧义消解、任务拆解 | 能力最强档 |
  | 明确规则下的抽取、转换、分类、格式化 | 中档 |
  | 大批量并发的机械节点（打标、过滤、去重） | 最快最省档 |
  | 与用户直接交互的主 Agent | 通常最强档 |

  默认继承调用方模型，仅在有明确理由（成本、延迟、能力不足）时覆盖，并在设计文档写明理由。**父子架构下不设默认**：每个子 Agent 的档位都要在步骤 3 逐个与用户确认。可考虑让验证/评审节点与生成节点使用不同模型以减少同源盲区，代价是风格差异与额外成本，按场景取舍。
- **工具授权**：从 `references/agent-construction.md` §三 的最小能力集起步，缺什么补什么，不要"先给全再收"。该表给的是能力类别，需按目标 harness 的实际工具名映射。授权解决"给哪些工具"，还要再定"这个动作它能不能自己拍板"——见 §授权与安全边界。
- **透明性**：Agent 的关键决策过程要对使用者可见（显式的计划步骤、选择理由），不要做成黑盒。

### 授权与安全边界

工具授权解决"给哪些工具"，这一节解决"**它能不能自己拍板**"与"**哪些内容不能信**"。事故的典型形态不是调错工具，而是调对了工具但不该由它自己决定；以及读进来的外部内容改写了它的目标。

**自主级别**：每个工具/动作四选一，在设计文档里标注。

| 级别 | 含义 | 典型 |
|---|---|---|
| `suggestion-only` | 只产出建议，由人或确定性代码决定是否执行 | 给出重构方案、生成待办清单 |
| `assisted-action` | 执行前需人确认单次动作 | 提交前展示 diff 等待确认 |
| `controlled-automation` | 自动执行，但限定在可回滚 / 可审计的范围内 | 在任务分支上自动改代码并提交 |
| `high-impact-automation` | 自动执行不可逆或高影响的动作 | 发消息给外部、扣款、改权限、删数据、部署 |

三条配套约束：

- **与用户直接交互的 Agent 默认只给前两档**；要给到第三档以上，在设计文档写明理由。
- **`high-impact-automation` 必须命名审批闸门**：不是写"需要审批"，而是写清**谁审、在哪一步审、审不过怎么办**。没有具名闸门的高影响自动化，视为设计未完成。
- **闸门是确定性代码，不是提示词纪律**。写在系统提示词里的"执行前请先确认"不算闸门——模型不遵守时没有任何东西拦得住。闸门必须是程序侧的拦截点。

**不可信输入**：Agent 读到的每一份外部内容（用户输入、网页、外部 API 返回、他人产出的文件、工具返回夹带的第三方内容、**子 Agent 的产出**）都是潜在的指令注入载体。三条底线：

- 不可信内容以**数据形式**传入（明确分隔与标注），**不得拼接进系统指令位置**。
- 不可信内容里的指令性文字**永不改变 Agent 的目标与授权**——提示词侧写死，工具层做兜底，两处缺一不可。
- 输出侧检查逐条具名并配**机器可读判定码**；检查自身出错时 **fail-closed**（抑制输出走兜底），绝不放行未检查的内容。

自主级别的标注格式、判档的三个常见误判（可回滚成本、读操作的下游影响、批量放大）与闸门写法见 `references/agent-construction.md` §三之二；信任分级表、判定码起步清单、fail-closed 的常见写反形态见 `references/safety.md`。命中判定与产出清单在步骤 2.7。

### 并发与任务拆分

在不损失任务质量的前提下，把相互独立的 Agentic 任务尽量拆小、提高并发数量，以降低总耗时与成本。四条约束：

- **相互独立**：拆出的任务之间不共享可变状态、不依赖彼此产出。有依赖关系的用流水线串联，不要硬并发。
- **不超过并发上限**：并发数受限于已确认的 LLM 并发额度（见 §各场景必确认项 通用项）。
- **不因拆分损失质量**：需要全局视野才能做的判断（跨文件综合、去重、排序、一致性校验）不要拆散；拆分后必须有汇总节点。
- **写明量化值**：拆分粒度与并发数是设计文档中要写死的量化项，不是运行时随意决定。

### 上下文管理

Agent 首次启动的 User Prompt 就要信息完备：

| 信息性质 | 处理 |
|---|---|
| 本次任务**必然**用到 | 直接写进提示词 |
| **可能**用到，篇幅只有几句 | 直接写进提示词 |
| **可能**用到，篇幅长（> 3k token） | 渐进披露：放进 Skill 或文本文件，提示词中只给**索引**。这些文件需提前归类整理好 |

- 复杂的流程、方法、经验，为了可复用应尽量集成进 **Skill**，便于迁移和加载。
- Agent 需读取的内容，若不经提示词传递，尽量用 **markdown 或 json** 存储。

### 注意力与认知负担

上下文管理解决"信息放哪里"，这一节解决"一次给多少"。目标：任一 Agent 在任一时刻，只面对当下这一步必需的信息。

五个抓手，设计期逐个 Agent 过一遍：

| 抓手 | 做法 | 过载信号 |
|---|---|---|
| **渐进披露** | 只把"本次必然用到"的写进提示词，其余留索引、用时再读 | 提示词塞满只有少数任务会用到的细则 |
| **分层管理** | 按变化频率归层：恒定约定 → 系统提示词；可复用方法与长资料 → Skill / 文件；本次数据 → 运行时传入 | 业务规则硬编码进多个 Agent 的提示词，改一次要动一片 |
| **场景分割** | 一个 Agent 只面对一类场景；多场景先路由，再进专用 Agent | 提示词里出现 3 段以上"如果是 X 类任务则……" |
| **任务拆解** | 每步只产出一样东西，且该产出能被下一步校验 | 一个节点要同时完成读取、判断、改写、汇总 |
| **逐步执行** | 长任务设检查点，中间状态落到外部载体（todo / 中间文件） | 关键中间结论只存在于对话历史，一压缩就丢 |

红线（触到即须处置，处置方式见步骤 2.6a）：

- 单个 Agent 系统提示词 > 10000 字符
- 首轮 User Prompt 内嵌 > 3k token 的"可能用到"资料
- 一个 Agent 的职责跨 3 个以上不相干领域
- 单轮任务预估上下文占用 > 上下文窗口的 50%
- 工具 / MCP 清单超出该 Agent 完成任务所需的最小集合

**与信息完备性的张力**：优先级以 §提示词质量 为准——先保证不遗漏（第 1 位），再降冗余（第 2 位）。减负只能通过**换放置层级**（下沉到 Skill / 文件并留索引）或**拆分职责**实现，**不得删掉 Agent 做判断必需的规则**。

### 长产物的构造方式

上一节管输入侧，这一节管输出侧：**不要让 Agent 一次性吐出一份长交付物**。改成「程序预建模板 → Agent 分区多次编辑 → 程序校验」。

适用判据（命中任一即走此法）：

- 预估产出超过模型单次输出上限的一半
- 交付物结构固定，且可切成 3 个以上互相独立的分区
- 同一份产物要由多个 Agent 或多个步骤共同填充

命中即改为三步：**程序建骨架**（写全分区标题、占位符、每区字段说明）→ **Agent 分区编辑**（一轮只填一个分区，只给该区所需上下文）→ **程序校验回流**（查占位符残留与必填分区，不合格只退回该区重填）。

**多 Agent、多步骤的 Agent-程序协作工作流，默认先按这个思想编排**：先定产物模板与分区表，再排谁填哪一区、按什么顺序填、谁来校验。

做法细则、分区划法、完整示例与反模式见 `references/long-artifact.md`；命中判定在步骤 2.6b。

### 工具返回的体量控制

上两节管 Agent 自己的输入与输出，这一节管**工具塞回来的量**。一次超长的工具返回能吃掉整轮上下文预算，而它的大小由外部数据决定——设计期看着没问题，上线撞上一个大仓库、一张大表、一个长日志就爆。这是上下文耗尽最常见的来源，且没有任何提示词纪律拦得住。

**检查范围**：返回**直接进入模型上下文**的工具与 MCP。Skill 内 CLI 与外部 CLI 通常不在此列——它们经 shell/bash 通道调用，由通道侧的统一截断/落盘兜底，CLI 自身提供 limit / 分页 / 摘要参数即可，不必逐个建极端用例。**自建 agent loop 时，通道工具的兜底就是你的工程职责，必须实现。**

**红线**：单次返回 > 10k token（≈ 40KB 英文 / ≈ 1.5 万汉字）视为超长，必须有处置。**同一轮内会被多次调用的工具（并行分片、循环翻页、批量入口）按单轮累计算**，不按单次。

两条处置路径，判据是**你改不改得了 agent loop**：

- **a. loop 侧统一落盘**（推荐）：执行循环发现返回超阈值即写文件，回给模型的是**路径 + 摘要 + 结构索引**，Agent 用读取 / 检索工具按需取用。有权改 loop / harness 时的默认选择——一处实现，覆盖现有与将来的所有工具，包括改不动的第三方 MCP。
- **b. 工具自身兜底**：服务端过滤、分页/游标、条数上限、默认摘要 + 明细开关。只覆盖你改得到的那些工具，每加一个工具就要重做一次判断。

走 b 的必须**建极端返回用例**：按最大规模输入实测最长返回的 token 数，落成回归用例。**实测仍 > 10k 的，停下来请用户确认是否改走路径 a。**

三条配套约束：

- **落盘不等于把信息丢掉**：返回里必须留下**导航信息**（总量、结构 / 字段概览、检索方式、文件路径），否则 Agent 拿不到它做判断所需的信息。与步骤 2.5 的完备性冲突时，完备性优先——改检索方式，不改成"不给了"。
- **落盘的内容仍继承原始信任级别**：外部数据不因为"存成了本地文件"就变可信，Agent 读回来时照样按不可信输入处理（见 §授权与安全边界）。
- **截断不是兜底**：直接砍掉尾部而不告知总量与获取方式，会让 Agent 拿着半截数据当全量用，比返回超长更危险。截断必须伴随"还有多少、怎么拿剩下的"。

估算换算、落盘返回契约、极端用例写法与常见超长源清单见 `references/tool-output.md`；命中判定在步骤 2.6c。

### 测试与评测

交付判据不是"整体跑通一遍"，而是**每一步都能单独验证**。三层，按场景取：

| 层 | 测什么 | 何时必须有 |
|---|---|---|
| **步骤级单元测试** | 每个节点：给定输入 → 产出是否符合契约 | Agentic 工作流 / 父子 Agentic：**每个步骤都要有** |
| **端到端用例** | 整条链路走通，含边界与异常输入 | 所有含 2 个以上节点的场景 |
| **批量评测集** | 一批代表性输入上的通过率与质量分 | 产出质量有波动，或要横向对比模型 / 提示词 / 分区方案的版本 |

单 Agentic / 单 Agent Chat 场景不涉及步骤级，按 `references/agent-construction.md` §四 做实跑测试即可；产出质量有波动时仍建议建评测集。

三条不可让渡的判据：**端到端不能替代步骤级**（前者只说"坏了"，后者才说"哪一步坏了"）；**能程序断言的一律程序断言**；**评测 Agent 上岗前必须用人工标注样本校准**，未校准的等于没有测试。

用例写法、评测 Agent 与 rubric 构建、批量评测与门禁见 `references/testing.md`。

## 各场景必确认项

完整提问批次见 `references/design-doc-template.md` §一。本节只列各场景**额外**的差异项。

### 通用（所有场景）

以下八项散落在 §一 的各批次中（按小节标题定位，不要按编号），此处强调它们**不可省略**，任何场景都要问到：

1. 场景分类结论与判定理由（含被排除的次优选项）。
2. **上下文上限**：需要的 LLM 上下文至少多少、是否足以完成任务；是否需要轮次限定或上下文压缩。
3. **并发上限**：用户提供的 LLM 链接通常有并发限制，除非用户明确说无限制。
4. **注意力分层方案**：各 Agent 的信息分成哪几层（系统提示词 / 按需加载 / 运行时传入），步骤 2.6a/2.6b 的触线处置是否认可。
5. **自主级别与审批闸门**：每个工具/动作的自主级别；高影响动作由谁审、在哪一步审、审不过怎么办。（单 Agent Chat 无工具，此项与第 8 项跳过；第 6 项不跳过。）
6. **不可信输入清单与安全检查项**：哪些来源视为不可信、输出侧有哪些具名检查与判定码、检查失败时的兜底行为。
7. **测试与评测方案**：步骤级用例覆盖到哪、非结构化产出怎么判、是否建评测集与门禁阈值（含安全切片）。
8. **工具返回体量与兜底**：哪些工具/MCP 的最大返回可能超 10k token、走 loop 落盘还是工具自兜底、极端返回用例由谁建。

### 单 Agent Chat 应用

无额外项。

### 单 Agentic 应用

1. **工具、MCP 清单**——通常给完成任务的**最小**集合。
2. **Skill 范围**（如有）——同样取最小范围。
3. **系统提示词内容对齐**——必须取得用户确认。建议在系统提示词所在代码/文档中记录**最近一次确认日期**；若时间过久且相关业务逻辑已更新，需再次与用户确认其可用性。

### 父子 Agentic 应用

1. 子 Agent 系统提示词是**父 Agent 实时构建**、**固定单一**，还是**固定若干个按需分配**？由用户决定并说明其顾虑。
2. 子 Agent 是否有数量上限？是多少？**是否超过 LLM 并发上限**？拆分粒度与并发数各是多少？
3. **每个子 Agent 的模型档位逐个确认**（此场景不设默认档位）。
4. **子 Agent 产出的信任处理**：父 Agent 采纳前是否做筛查、子 Agent 读了哪些不可信来源。子 Agent 的产出继承其输入中最低的信任级别，不因"是我派出去的"就当可信——污染会沿链路向上传播。
5. 对子 Agent 再走一遍「单 Agentic 应用」的 3 项确认。

### Agentic 工作流

**先选编排模式**，再谈具体步骤：

| 模式 | 何时用 | 例子 |
|---|---|---|
| Prompt Chaining | 任务能干净拆成固定顺序的子任务，每步之间可加校验门 | 提纲 → 初稿 → 校对 |
| Routing | 输入有互斥类别，分类后交由不同处理器效果更好 | 客服工单按类型分流 |
| Parallelization | 可分块提速（分块），或需多视角交叉验证（投票） | 一份文档由合规、财务、法务三视角并行审 |
| Orchestrator-Workers | 子任务无法预先列出，需运行时动态拆解 | 按代码库实际结构决定审计哪些模块 |
| Evaluator-Optimizer | 有明确评价标准，且迭代能带来可测收益 | 生成 → 评分 → 按反馈重写，直到达标 |

选中 **Orchestrator-Workers** 意味着该工作流内部嵌套了父子 Agentic，需同时走完 §父子 Agentic 应用 的确认项。Parallelization 与 Orchestrator-Workers 的分界线与步骤 1 相同：子任务是否预定义。

其余确认项：

1. **整体输入、输出**的格式与形态。产出较长或由多步骤共同填充时，**先定产物模板与分区表**（见 §长产物的构造方式），再排步骤——这是本场景的默认编排姿势。
2. **SOP 详细设计 + 流程图确认**：按工作先后次序描述，每一步标明由**程序**还是 **Agent** 执行；Agent 节点的工作流程、分支条件；并行部分如何并行。**这个过程必须用业务语言与用户沟通**。
3. **信息连续性**：确认程序与 Agent 之间每一步的沟通方式（文件 / 结构体 / Prompt），确保传递准确、无遗漏、无冗余。注意：**工具通常不作为流程环节**，它是 Agent 可选用的操作。

### 完全程序过程

无需语义判断即可完成 → 转程序开发模式，**不继续本 skill**。

## 约束

1. 除非用户明确要求跳过核对，否则步骤 3 未取得确认不得进入实现；跳过时须把关键假设写入设计文档的「确认记录」一节 并告知用户。
2. 评审已有实现时，先独立出设计再比对，不得被现有实现锚定。
3. 不把 `references/system-prompt-blocks.md` 整块复制进系统提示词——只摘条件命中的块。
4. 设计文档写入 `docs/specs/YYYY-MM-DD-<short-desc>.md` 并同步 `docs/index.md`（若项目另有文档治理规则，以项目规则为准）。
5. 场景判定命中「完全程序过程」时如实告知用户，不为了用上 Agent 而 Agent 化。
6. 注意力减负**不得删除 Agent 做判断必需的规则**；下沉层级与拆分职责是首选手段。删除真正冗余的内容（重复、模型已知的常识、与本 Agent 职责无关的段落）不受此限。
7. 评审场景发现的注意力问题，须先与用户确认成立，再提改进建议；不得直接改动现有实现。
8. 命中 §长产物的构造方式 判据的交付物，模板由**程序**预建、完整性由**程序**校验，**不以 Agent 自评替代程序校验**（自检仍是好习惯，只是不能当验收依据）。
9. 多节点场景不得只做端到端测试；每个步骤都要有可单独运行的用例。评测 Agent 未经人工标注样本校准，不得作为验收依据。
10. 每个工具/动作都要标自主级别；`high-impact-automation` 必须有**确定性代码实现**的具名审批闸门，提示词里的"执行前请先确认"不算闸门。
11. 走增量入口时，平台缺口清单必须逐条对照并处置（补 / 登记为风险 / 记未踩中），不得以"平台一直这样"默认继承。
12. 直接进入模型上下文的工具/MCP 都要按最坏情况估算最大返回；估算或实测 > 10k token 而无兜底的，**不得在未告知用户的情况下交付**——用户明确接受该风险的，记入设计文档「确认记录」后可放行。由工具自身兜底的必须有极端返回用例，实测仍超线时请用户裁决是否改走落盘-读取，不得以"一般不会那么大"自行放行。

### 绝对禁止

- **绝对禁止**将真实凭证、密钥、客户数据写入设计文档或提示词示例——一律使用占位符。设计文档会进入 `docs/` 并可能入库，提示词会分发给多个 Agent。
- **绝对禁止**设计不设数量上限的子 Agent 派发，或上限高于已确认的 LLM 并发额度。
- **绝对禁止**以合理推测填补信息缺口：未经用户确认的业务规则，不得写入 Agent 提示词或 Skill。
- **绝对禁止**把不可信内容拼接进系统指令位置（系统提示词、工具描述、SOP 段落、评测 rubric）。
- **绝对禁止**对超长返回做**静默截断**：砍掉尾部而不告知总量与获取剩余部分的方式，会让 Agent 把半截数据当全量用，且下游无从察觉。截断必须伴随"还有多少、怎么拿剩下的"。
- **绝对禁止**安全检查或审批闸门 fail-open：检查逻辑异常、闸门服务不可用时，一律视为未通过，抑制输出走兜底，不得放行。

## 失败处理

| 情况 | 动作 |
|---|---|
| 用户意图模糊，且不同理解会导致不同场景选型 | 停下提问，不要先做设计 |
| 用户坚持一个你判定为过度 Agent 化的方案 | 用一两句说明代价（成本/延迟/不确定性），用户重申后按用户方案推进 |
| 用户要求跳过核对直接实现 | 允许跳过，但必须把全部关键假设写入设计文档的「确认记录」一节，并一句话告知用户"已按以下假设推进" |
| 用户对提问答复"你定就行" | 给出带理由的默认值，标注为假设写入设计文档的「确认记录」一节，继续推进，不要反复追问 |
| 目标项目没有 `docs/` 目录 | 创建 `docs/specs/` 并新建 `docs/index.md` 索引 |
| 步骤 2.5 发现资料不足以支撑业务判断 | 列出缺口清单交用户补充，不要让 Agent"自由发挥"顶上 |
| 步骤 2.6a 的减负处置与 2.5 的完备性要求冲突 | 完备性优先，改用下沉或拆分实现减负，不删规则 |
| 用户不认可评审中提出的注意力问题 | 记为"用户判定非问题"关闭，不反复申辩，也不擅自改动 |
| Agent 产出被输出上限截断，或长文档反复重写仍有遗漏 | 不要靠"再试一次"或换更大模型，改走 §长产物的构造方式：程序建模板 + 分区编辑 + 程序校验 |
| 某个工具的返回体量取决于外部数据，估不准 | 按最坏情况构造极端用例实测，用实测值填清单；不接受"一般不会那么大"这类推测 |
| 工具自身兜底后实测仍 > 10k token | 停下来请用户确认是否改走 loop 侧落盘-读取；未获确认前不按现状交付 |
| 目标 harness 不支持超长返回自动落盘，且改不了 loop | 登记为平台缺口，在工具层实现落盘并返回路径 + 摘要 + 检索方式；第三方 MCP 改不动的，显式登记为风险交用户裁决 |
| 上下文频繁被单次工具调用打满，但说不清是哪个工具 | 缺工具返回体量清单。按步骤 2.6c 逐个工具估算 + 实测补齐，不要靠调大上下文窗口绕过 |
| 端到端跑通但结果时好时坏，定位不到是哪一步 | 缺步骤级用例。按 `references/testing.md` §二 给每个节点补夹具与契约断言，不要靠反复整链重跑猜 |
| 某个节点的输入无法脱离上游单独构造 | 这是信息传递链路定义不清，回设计文档的「信息传递链路」一节补齐，不要改成"只能整链测" |
| 评测 Agent 的判定与人工判断经常不一致 | 先改 rubric 判分锚点，再改评测 Agent 的提示词；校准通过前不得用它做验收 |
| 某个动作不可逆或高影响，但用户没指定谁来审批 | 停下来问，不得默认为自动执行；问不到答复时按 `assisted-action` 落地并在设计文档标注 |
| 用户要求"别老是弹确认，直接做" | 说明哪些动作不可逆、代价是什么，用户重申后按其要求下调级别，并把决定写进「确认记录」；`high-impact-automation` 的闸门仍要具名，只是审批方可能变成用户自己 |
| 需求只是在既有平台上加一个 skill / 工具 | 走增量入口，不要重跑完整新建流程；但先过一遍 `references/incremental.md` §一 的退回信号 |
| 增量需求撞上平台已知缺口（无闸门、无用例、返回未筛查） | 能在能力层补的就补，补不了的显式登记为风险并标注影响，交用户裁决；不静默继承 |
| 增量场景找不到某项基线的继承来源 | 这不是"继承"而是"未知"，登记进平台缺口清单，不要写"沿用现有做法"含糊过去 |
| 现有实现与设计差异过大、改造成本高 | 输出差异清单并标注成本，由用户裁决范围，不擅自缩小或扩大 |
| 既有设计文档的 `skillVersion` 与当前版本不符 | 按小节标题名定位而非编号；告知用户差异，询问是否按新模板补齐缺失小节 |

## 按需引用

- `references/agent-construction.md`：设计具体某个 Agent（写系统提示词、定工具授权、做交付前测试）时读。含六要素模板、写作细则、最小能力集、实跑测试步骤。
- `references/system-prompt-blocks.md`：写或改 Agent 系统提示词时读。含增益提示块全文与适用条件矩阵。
- `references/design-doc-template.md`：进入步骤 3 时读。含完整提问批次（权威版本）、设计文档骨架、流程图写法。
- `references/long-artifact.md`：步骤 2.6b 判定命中长产物判据时，或实现阶段搭产物模板时读。含三步做法、分区划法、完整示例。
- `references/tool-output.md`：步骤 2.6c 估工具返回体量时读，实现阶段做落盘兜底、写极端返回用例、评审阶段核对返回体量时也读。含估算换算、两条处置路径的落地、落盘返回契约、用例写法、常见超长源清单。
- `references/safety.md`：步骤 2.7 定不可信输入与输出检查时读，实现阶段搭检查点、评审阶段核对安全边界时也读。含信任分级表、判定码起步清单、fail-closed 要求、安全样本切片。
- `references/testing.md`：进入步骤 4，或评审现有实现的测试完备性时读。含三层测试执行要点、步骤级用例写法、评测 Agent 与 rubric 构建、批量评测与门禁。
- `references/incremental.md`：入口判定为「增量」时读，新建与评审场景不读。含入口判定与退回信号、继承声明、只 spec 增量、平台缺口清单。
- `references/review-mode.md`：入口判定为「评审已有实现」时读，新建场景不读。含六项评估的动作序列、证据要求、边界。

交付前确认。

- [ ] 场景分类有明确结论，且给出了判定理由，并已在该场景上限内取最低可行档
- [ ] （工作流场景）编排模式已选定
- [ ] 每个 Agent 的系统提示词六要素齐全，且含必选的「开工前自检」块
- [ ] 每个 Agent 的模型档位与工具授权已定，覆盖默认档位的均写明了理由
- [ ] 工具/MCP/Skill 清单是最小集合，且描述覆盖了隐式规则
- [ ] 上下文上限、并发上限已与用户确认；拆分粒度与并发数已写死
- [ ] 步骤 2.5 已逐个 Agent 扫描，缺口已列出并交用户处理
- [ ] 步骤 2.6a 已逐个 Agent 核对红线，触线项均有处置（下沉 / 拆分 / 加路由 / 加检查点）
- [ ] 步骤 2.6b 已逐个 Agent 核对产物判据；命中项已有程序预建模板、分区表与程序侧校验规则
- [ ] 步骤 2.6c 已逐个工具/MCP 按最坏情况估算最大返回；触线项已定处置路径（loop 落盘 / 工具自兜底）与兜底实现位置，触线与灰区项已排定极端返回用例
- [ ] 走返回落盘方案的 Agent 已授权文件读取 + 内容检索能力（否则落盘等于把信息删了）
- [ ] 长任务的检查点与中间状态载体已明确，关键中间结论不只存在于对话历史
- [ ] 程序与 Agent 间的信息传递链路逐步骤明确
- [ ] 步骤 2.7 已逐个工具标出自主级别；`high-impact-automation` 均有具名审批闸门（谁审 / 哪一步 / 不通过怎么办）与程序侧实现位置

- [ ] 输出侧安全检查项已具名并配判定码，各自的执行者与执行时机已定，检查失败时 fail-closed

- [ ] 每个 Agent 已实跑测试（≥1 个典型任务 + 1 个边界情况），不符项已回改并重跑
- [ ] （多节点场景）每个步骤有可单独运行的用例，含典型 / 边界 / 异常输入，结构断言已程序化
